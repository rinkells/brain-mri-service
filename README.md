# Сервіс класифікації МРТ мозку

> **Увага: це навчальний проєкт, а не медичний виріб.**
> Сервіс створено в межах дипломної роботи. Він не проходив клінічних випробувань і
> сертифікації, тому його результати не можна використовувати для діагностики, вибору
> лікування чи будь-яких інших медичних рішень.

Сервіс приймає знімок МРТ мозку (JPEG або PNG) і визначає один із чотирьох класів:
гліома (`glioma`), менінгіома (`meningioma`), пухлина гіпофіза (`pituitary`) або відсутність
пухлини (`notumor`). Разом із класом він повертає ймовірності всіх класів, попередження про
надійність результату і, за бажанням, теплову карту Grad-CAM. Аналіз доступний без
реєстрації; результати прогнозів зареєстрованого користувача зберігаються в його власній
історії (PostgreSQL), яку бачить лише він (див. «Автентифікація»).

> **Знімки не зберігаються.** В історію потрапляє лише результат прогнозу: клас,
> ймовірності, розмір знімка, попередження, час обробки і версія моделі. Самого зображення,
> назви файлу чи його хешу сервіс не зберігає ні в базі, ні в журналах, бо це медичні дані.
> Під час обробки запиту файл до 1 МБ тримається в пам'яті, а більший FastAPI (Starlette)
> тимчасово записує в системну тимчасову теку (у Docker — `/tmp` контейнера). Після запиту
> цей тимчасовий файл видаляється.

Проєкт складається з трьох частин:

- **бекенд** (`backend/`) — FastAPI-сервіс із моделлю ResNet18 із torchvision, останній шар
  якої замінено на шар із чотирма виходами. Ваги `resnet18_v2c_best.pt` (версія
  `resnet18_v2c`) навчено окремо; у репозиторії їх немає;
- **база даних** — PostgreSQL 16 для історії прогнозів; схема ведеться міграціями Alembic;
- **вебінтерфейс** (`frontend/`) — React + TypeScript на Vite, стилі на Tailwind CSS. У
  Docker Compose зібраний інтерфейс роздає nginx, який і пересилає запити до API.

## Швидкий старт

Потрібні Docker Desktop (або Docker Engine з Compose v2) і файл ваг у
`backend/models/resnet18_v2c_best.pt`.

```powershell
Copy-Item .env.example .env   # і задайте в .env власний POSTGRES_PASSWORD
docker compose up --build
```

Відкрийте <http://localhost:8080>. Подробиці — у наступному розділі.

## Запуск через Docker Compose

Найпростіший спосіб запустити весь застосунок: інтерфейс, бекенд і базу. Потрібен Docker
Desktop (або Docker Engine з Compose v2).

1. Покладіть файл ваг у `backend/models/resnet18_v2c_best.pt`.
2. Скопіюйте шаблон змінних і задайте пароль бази:

   ```powershell
   Copy-Item .env.example .env
   ```

   У `.env` замініть `POSTGRES_PASSWORD=change-me` на власний пароль. Пароль стає
   частиною адреси бази, тому використовуйте лише латинські літери, цифри, `-` і `_`.
   Файл `.env` у git не потрапляє; у репозиторії лежить лише `.env.example`.
3. Зберіть і запустіть:

   ```powershell
   docker compose up --build
   ```

4. Коли всі три сервіси стануть здоровими (`docker compose ps`), відкрийте
   <http://localhost:8080>.

Compose запускає три сервіси:

- **`db`** — `postgres:16`; дані зберігаються в томі `pgdata` і переживають перезапуск;
  готовність перевіряється `pg_isready`;
- **`api`** — образ із `backend/`; стартує лише після того, як `db` стане здоровим, спершу
  виконує `alembic upgrade head`, а потім запускає `uvicorn`. Тека `backend/models`
  монтується лише для читання. Здоровим вважається, коли `GET /health/ready` відповідає 200
  (див. «Перевірки стану: liveness і readiness»);
- **`frontend`** — образ із `frontend/`. На першому етапі Node збирає інтерфейс (`npm ci`,
  `npm run build`), на другому `nginxinc/nginx-unprivileged` роздає збірку від
  непривілейованого користувача на порту 8080 і пересилає запити API до `api`. Стартує
  після того, як `api` стане здоровим.

Після запуску:

- інтерфейс: <http://localhost:8080>;
- API: <http://127.0.0.1:8000>, документація: <http://127.0.0.1:8000/docs>;
- Postgres доступний з цього комп'ютера на `127.0.0.1:5433` (порт змінюється в `.env`).

Усі порти відкрито лише на `127.0.0.1`: HTTPS немає, тож паролі й cookie сесії йшли б
мережею відкритим текстом.

### Як влаштовано

```
браузер ──► nginx (frontend, 127.0.0.1:8080) ──► api:8000 (FastAPI) ──► db:5432 (Postgres)
              ├ роздає зібраний інтерфейс
              └ пересилає /health, /predict, /predictions, /stats, /auth/*
```

Браузер звертається лише до nginx, тож інтерфейс і API мають одне джерело і CORS не
потрібен. nginx пересилає тільки шляхи, які потрібні інтерфейсу (ті самі, що й проксі Vite
у розробці). Swagger UI, ReDoc і схема API через nginx недоступні: вони лишаються на
порту API. `/health/ready` теж: nginx сам відповідає на нього 404 (див. «Перевірки стану:
liveness і readiness»).

**Host і Origin.** nginx передає API заголовок `Host` таким, яким його надіслав браузер
(`localhost:8080`), і не змінює `Origin`. Тому:

- `ALLOWED_HOSTS` має містити хост, за яким відкрито інтерфейс; `localhost` і `127.0.0.1`
  дозволені завжди. Якщо відкрити інтерфейс за іншою адресою (наприклад, за IP у
  локальній мережі), API відповість 400, а інтерфейс покаже «Адресу сервера не дозволено»;
- для `POST` і `DELETE` браузер надсилає `Origin: http://localhost:8080` (або
  `http://127.0.0.1:8080`), тому обидва значення додано до типового `ALLOWED_ORIGINS` у
  `docker-compose.yml` і в обидва `.env.example`. Без них аналіз і видалення отримували б
  403.

nginx також задає заголовок `X-Real-IP` — адресу клієнта, як її бачить nginx, замість
будь-якого значення від самого клієнта, — і додає `X-Forwarded-For`. За `X-Real-IP` API
рахує ліміт частоти запитів (див. «Rate limiting»).

Cookie сесії nginx передає в обидва боки без змін: `Set-Cookie` від API до браузера і
`Cookie` від браузера до API. Cookie прив'язана до хоста, але не до порту: після входу на
`localhost:8080` браузер надсилає її й на `localhost:8000`, але не на `127.0.0.1:8000`
(це інший хост).

**Мережа.** Compose задає мережі фіксовану підмережу `172.30.250.0/24`, а контейнеру
`frontend` — фіксовану адресу `172.30.250.10`: лише їй API вірить як проксі
(`TRUSTED_PROXIES`). Інші контейнери отримують адреси з `172.30.250.128/25`, і з цього ж
діапазону Docker бере адресу шлюзу мережі: `172.30.250.128`, а не `.1`. Якщо ця підмережа на
вашому комп'ютері вже зайнята, змініть разом підмережу, адресу `frontend` і
`TRUSTED_PROXIES` у `docker-compose.yml`.

Які адреси насправді видно (перевірено під Docker Desktop у Windows):

| Звідки запит | Що бачить nginx (`$remote_addr`) | Що бачить API (адреса з'єднання) | Ключ ліміту |
|---|---|---|---|
| браузер чи curl на цьому комп'ютері → `localhost:8080` | `172.30.250.128` (шлюз) | `172.30.250.10` (nginx) | `172.30.250.128` з `X-Real-IP` |
| curl на цьому комп'ютері → `127.0.0.1:8000` напряму | — | `172.30.250.128` (шлюз) | `172.30.250.128` |
| healthcheck усередині контейнера `api` | — | `127.0.0.1` | `/health/ready` не рахується |

Підроблені `X-Real-IP` чи `X-Forwarded-For` нічого не змінюють: через 8080 nginx
перезаписує `X-Real-IP`, а напряму на 8000 шлюз не входить до `TRUSTED_PROXIES`, і uvicorn
запущено з `--no-proxy-headers`.

Під час оновлення з версії без фіксованої підмережі Compose не змінює вже створену мережу,
і `docker compose up` зупиняється з помилкою `no configured subnet or ip-range contain the
IP address 172.30.250.10`. Тоді один раз виконайте `docker compose down` (без `-v`: том
`pgdata` з історією лишається) і знову `docker compose up --build`.

**Ліміт файлу.** `MAX_UPLOAD_MB` з `.env` отримують і бекенд, і збірка інтерфейсу (як
`VITE_MAX_UPLOAD_MB`), тож обидва перевіряють той самий розмір. nginx пропускає тіла
запитів до 12 МБ (`client_max_body_size` у `frontend/nginx.conf`), тобто трохи більше за
типові 10 МБ: файл, трохи більший за ліміт, доходить до API, і той відповідає 413 зі своїм
поясненням. nginx цей ліміт із `.env` не читає: якщо підняти `MAX_UPLOAD_MB` вище за 10,
треба змінити `client_max_body_size` у `frontend/nginx.conf` (на 1–5 МБ більше) і
перезібрати `frontend` (`docker compose up -d --build frontend`).
Знімки й теплові карти `/predict` проходять через nginx наскрізь, без буферизації, а
відповіді nginx чекає до 120 секунд.

**Заголовки безпеки.** nginx додає до кожної відповіді `Content-Security-Policy` (лише
власні скрипти, стилі й запити; зображення ще з `data:` і `blob:` для теплової карти й
прев'ю), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` і
`Referrer-Policy: no-referrer`. Вбудований скрипт теми в `index.html` дозволено за його
хешем SHA-256: якщо змінюєте цей скрипт, оновіть хеш у `nginx.conf` (тест у
`backend/tests/test_deployment.py` нагадає). Файли з хешем у назві (`/assets/`)
кешуються надовго, а `index.html` браузер перевіряє щоразу.

Контейнерам задано ліміти, щоб один збійний запит чи сервіс не забрав усю машину:

| Сервіс | Ліміти | Навіщо |
|---|---|---|
| `api` | `mem_limit: 1500m`, `cpus: 2`, `pids_limit: 200`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]` | Пам'ять і процесор для моделі та `MAX_CONCURRENT_INFERENCES` одночасних прогнозів. Сервер працює від непривілейованого користувача на порту 8000, тому Linux-можливості (capabilities) йому не потрібні, і нових він отримати не може |
| `db` | `mem_limit: 512m`, `pids_limit: 256` | Postgres запускає окремий процес на кожне з'єднання: 256 вистачає на 100 з'єднань (типове `max_connections`) і фонові процеси. Можливості не обмежено: точці входу образу потрібно змінити власника теки з даними й перейти на користувача `postgres` |
| `frontend` | `mem_limit: 128m`, `pids_limit: 64`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `read_only: true`, `tmpfs: /tmp` (16 МБ) | nginx лише роздає файли й пересилає запити. Файлова система контейнера доступна лише для читання; pid-файл і тимчасові файли nginx лежать у `/tmp` у пам'яті |

Пам'ять `api` виміряно поза Docker (Windows, справжні ваги): ≈ 400 МіБ після старту,
до ≈ 1040 МіБ на мить під час завантаження torch і до ≈ 780 МіБ під час двох одночасних
прогнозів знімка 4096 × 4096 із Grad-CAM. Якщо збільшуєте `MAX_CONCURRENT_INFERENCES`,
збільште й `mem_limit`: коли контейнер виходить за ліміт, ядро завершує процес, і Compose
перезапускає `api` (`restart: unless-stopped`).

### Перевірки стану: liveness і readiness

API має два шляхи для перевірки стану, і вони відповідають на різні питання:

| | `GET /health` — liveness | `GET /health/ready` — readiness |
|---|---|---|
| Питання | Чи живий процес? | Чи готовий сервіс до повної роботи? |
| Що перевіряє | Лише те, що сервер відповідає | Модель завантажена **і** база (якщо задано `DATABASE_URL`) відповідає на `SELECT 1` не довше ніж за 2 с |
| База | Не опитується | Окреме нове з'єднання на кожну перевірку, в окремому потоці поза циклом подій; результат живе 2 с; без `DATABASE_URL` не опитується |
| Коли база недоступна | 200 | 503, `"database": false` |
| Без `DATABASE_URL` | 200 | 200, `"database": null` |
| Відповідь | `status`, `device`, `classes`, `model_version` (їх читає інтерфейс) | `status` (`ready` або `not_ready`), `model`, `database`; `Cache-Control: no-store` |
| Хто користується | індикатор стану в інтерфейсі; `HEALTHCHECK` образу бекенду | healthcheck сервісу `api` у Docker Compose |

Обидва шляхи не обмежуються лімітом частоти, не потребують сесії (cookie, навіть
прострочена, ігнорується) і не відхиляються перевіркою запитів зі сторінок інших сайтів.
Тіло 503 від `/health/ready` не містить ні тексту помилки, ні адрес чи імен: причину видно
лише в журналі API (`Readiness: the database is unreachable (...)`), і пишеться вона лише
тоді, коли стан змінюється, а не на кожну перевірку.

**Де доступний `/health/ready`.** Він показує, чи працює база, тому не виставлений через
nginx: на порту 8080 nginx сам відповідає на нього 404 (без цього правила запасний
`index.html` інтерфейсу віддавав би 200), а проксі Vite у розробці його не пересилає.
Шлях доступний усередині Compose (healthcheck питає `127.0.0.1:8000` у контейнері `api`) і
на порту API `127.0.0.1:8000`. `/health` (liveness) інтерфейс читає, тож nginx його
пересилає.

Поле `database` має три значення:

- `true` — `DATABASE_URL` задано, і база відповіла;
- `false` — `DATABASE_URL` задано, але база не відповіла за 2 с: 503;
- `null` — `DATABASE_URL` не задано, тобто сервіс навмисно працює без бази (прогнози без
  історії й входу). Тоді база не є залежністю, не перевіряється, і готовність залежить лише
  від моделі: 200 `{"status": "ready", "model": true, "database": null}`.

**Що використовує Compose.** Healthcheck сервісу `api` у `docker-compose.yml` питає
`/health/ready` кожні 10 секунд (`timeout` 5 с, 3 спроби, перші 60 с на міграції й
завантаження моделі не рахуються) і замінює `HEALTHCHECK` самого образу, який питає
`/health`: контейнер, запущений з образу без Compose і без бази, не має ставати
нездоровим. `frontend` стартує лише після того, як `api` стане здоровим, тобто коли модель
завантажена, а база доступна.

Якщо базу зупинити (`docker compose stop db`), `/health/ready` за кілька секунд (кеш 2 с і
до 2 с очікування перевірки: ім'я `db` зупиненого контейнера Docker DNS розв'язує повільно)
починає відповідати 503, а `/health` — 200, і інтерфейс працює далі: прогнози повертаються без збереження (див.
«Якщо база недоступна»). Приблизно за 30 секунд (3 невдалі перевірки) `docker compose ps`
показує `api` як `unhealthy`. Docker не перезапускає нездоровий контейнер, і це не
потрібно: коли база повертається, `/health/ready` знову відповідає 200, а `api` стає
`healthy` після наступної перевірки.

**Як перевіряється база.** Кожна перевірка відкриває нове з'єднання власним рушієм
(`NullPool`, `application_name = brain-mri-readiness` у `pg_stat_activity`) і закриває його
одразу після `SELECT 1`. Спільного пулу, з якого беруть з'єднання прогнози й історія, вона не
торкається: навіть коли всі його з'єднання зайняті, здорова база не виглядає недоступною, а
мертве з'єднання з пулу не може підвісити перевірку. Перевірка йде в окремому потоці-демоні,
поза циклом подій.

Межі часу задає драйвер, і кожна діє лише на своїй ланці; у загальну межу на перевірку
вони не складаються:

| Ланка | Ліміт | Що його задає |
|---|---|---|
| Підключення: TCP, старт сесії, автентифікація | 2 с | `connect_timeout` |
| `SELECT 1` на працюючому сервері | 1 с | `statement_timeout` (стежить сервер) |
| Мережа перестала підтверджувати надіслані дані (обрив без RST) | 2 с | `tcp_user_timeout` |
| `SELECT 1` підтверджено, але відповідь не приходить, бо мережа зникла надовго | ≈ 3 с | TCP keepalive (`keepalives_idle` 2 с, `keepalives_interval` 1 с; без нього — системні ≈ 2 год). Коли саме обірвати з'єднання, на Linux вирішує `tcp_user_timeout` (2 с): на першій же пробі після 2 с без відповіді, тож `keepalives_count` (3) не встигає вплинути |

Запит до `/health/ready` чекає на перевірку не довше за 2 с, а тоді отримує 503; сама
перевірка йде далі. Де жоден ліміт не діє:

- розв'язання імені хоста (`db`) до TCP-з'єднання;
- сервер, ядро якого працює, а процес заморожено, коли `SELECT 1` уже надіслано
  (`docker pause` саме посеред перевірки): ядро підтверджує і дані, і проби keepalive.
  Перевірку, що почалася під час паузи, обриває `connect_timeout`.

Така перевірка висить, доки не відповість резолвер чи база.

**Одна жива перевірка.** Поки перевірка триває, нова не починається, хоч би скільки вона
висіла: кожен запит чекає на неї до 2 с і отримує 503 з `"database": false`. Коли зависла
перевірка завершиться, вона оновить стан, і наступний запит після закінчення кешу запустить
нову. Тож потік перевірки завжди щонайбільше один.

**Кеш 2 с.** Шлях не обмежено лімітом, тому результат перевірки (і успіх, і невдача)
віддається повторно протягом 2 с, а нова перевірка в цей час не починається. Разом з
однією живою перевіркою це означає, що навіть безперервний потік запитів дає не більше
одного з'єднання з базою за 2 с.

**Журнал.** Стан бази й записи в журналі змінює лише сама перевірка, і лише коли стан
змінюється. Запит, який не дочекався відповіді, нічого не пише. Тож повільна, але успішна
перевірка не дає хибних «база недоступна» й «знову відповідає». Перевірку, що висить,
жоден дедлайн не обриває: це свідомий компроміс, бо так жива перевірка лише одна і нових
потоків не з'являється. Щоб зависання не минало непомітно, перший запит, який дочекався
своїх 2 с, коли перевірка вже триває понад 10 с, один раз на перевірку пише
`Readiness: the check has been running for more than 10 s`. Крім цього рядка про
зависання кажуть відповіді 503 і `unhealthy` у `docker compose ps`.

Після початку зупинки (`close()`) перевірка, що завершується пізно, нічого не пише в
журнал: процес тоді може вже завершуватися, а запис у stderr із потоку-демона під час
завершення інтерпретатора здатен його аварійно зупинити.

**Зупинка.** На завислу перевірку при зупинці `api` не чекають: її потік — демон. Рушії
бази закриваються в окремому потоці, не блокуючи цикл подій, і зупинка чекає на них не
довше за 1 с.

curl.exe -i http://localhost:8080/health/ready   # через nginx: 404

## Запуск у розробці

**Термінал 1 — бекенд** на <http://127.0.0.1:8000>:

```powershell
.\.venv\Scripts\Activate.ps1
cd backend
uvicorn app.main:app --reload --port 8000 --no-proxy-headers
```

`--no-proxy-headers` вимикає власну обробку заголовків проксі в uvicorn: інакше він брав би
адресу клієнта з `X-Forwarded-For` у запитів від `127.0.0.1` (а через проксі Vite всі запити
приходять саме звідти), і клієнт міг би підмінити ключ ліміту частоти запитів. Адресу за
проксі визначає сам застосунок (див. «Rate limiting»).

Без `DATABASE_URL` бекенд працює, але історію не веде: прогнози повертаються з `"id": null`,
а `/predictions` і `/stats` відповідають 503. Щоб увімкнути історію, підніміть лише базу з
Compose і вкажіть її адресу в `backend/.env`:

```powershell
docker compose up -d db
# у backend/.env (пароль — той самий, що в кореневому .env):
# DATABASE_URL=postgresql+psycopg://brain_mri:<пароль>@127.0.0.1:5433/brain_mri
cd backend
alembic upgrade head
uvicorn app.main:app --reload --port 8000 --no-proxy-headers
```

Інтерактивна документація API: <http://127.0.0.1:8000/docs>.

**Термінал 2 — вебінтерфейс** на <http://localhost:5173>:

```powershell
cd frontend
npm run dev
```

Відкрийте <http://localhost:5173>. Браузер звертається лише до сервера Vite, а той
пересилає запити `/health`, `/predict`, `/predictions`, `/stats` і `/auth/*` на бекенд
(див. `server.proxy` у `frontend/vite.config.ts`; `/health/ready` не пересилається, ключ
`/health` там закріплено регулярним виразом). Тому налаштовувати CORS на бекенді не
потрібно.
Проксі передає бекенду заголовки браузера `Host` і `Origin` (`localhost:5173`), тож вони
мають бути в `ALLOWED_HOSTS` і `ALLOWED_ORIGINS`; типові значення це враховують. Якщо порт
5173 зайнятий, Vite не перейде на інший (`strictPort`), а зупиниться з помилкою: з іншого
порту аналіз і видалення відповідали б 403.
Якщо додаєте в API новий шлях, додайте його і в цей список, і у `frontend/nginx.conf`
(тест деплою перевіряє, що вони збігаються).

Якщо бекенд не запущено, індикатор у шапці показує «Сервіс недоступний», а спроба аналізу
закінчується повідомленням «Сервер недоступний».

## Можливості інтерфейсу

Сторінка **«Аналіз»**:

- вибір знімка кнопкою або перетягуванням, прев'ю вибраного файлу;
- перевірка формату (JPEG, PNG) і розміру файлу ще до відправки;
- перемикач «Показати теплову карту» і кнопка «Проаналізувати» зі станом завантаження;
- передбачений клас, смужки ймовірностей для чотирьох класів, знімок і теплова карта поруч;
- якщо зображення не схоже на знімок МРТ (`not_mri_like`), над результатом з'являється
  жовтий блок із текстом попередження; якщо модель недостатньо впевнена (`low_confidence`),
  під ним з'являється ще один жовтий блок; розмір знімка не 512 × 512
  (`unexpected_image_size`) позначається дрібною сірою приміткою під результатом; інші
  попередження сервера показуються в жовтому блоці;
- позначка, чи збережено результат в історії;
- зрозумілі повідомлення про помилки 400, 413, 415, 422, про зайнятий сервер (503) і про
  недоступний сервер;
- окремі повідомлення, коли сервер відхиляє запит через перевірку адрес: «Адресу сервера не
  дозволено» (інтерфейс відкрито за адресою, якої немає в `ALLOWED_HOSTS`, наприклад за IP у
  локальній мережі) і «Цій сторінці заборонено надсилати запити» (сторінки немає в
  `ALLOWED_ORIGINS`). Обидва підказують, яке налаштування сервера перевірити, і не радять
  просто повторити спробу.

Сторінка **«Історія»**:

- статистика: кількість прогнозів, частка з будь-яким попередженням і окремо частки
  «Не схоже на МРТ», «Низька впевненість» і «Нетиповий розмір знімка», середній час
  обробки, розподіл за класами;
- таблиця прогнозів (час, клас і версія моделі, впевненість, розмір знімка, попередження)
  по 10 на сторінку, від найновішого. Жовті позначки — «Не схоже на МРТ» і «Низька
  впевненість»; нетиповий розмір знімка позначено дрібним сірим текстом, повне
  повідомлення — у підказці;
- фільтр за класом;
- видалення запису з підтвердженням;
- повідомлення, якщо історію вимкнено або база недоступна.

**Вхід і реєстрація** (див. також «Автентифікація»):

- у шапці для гостя посилання «Увійти» і «Зареєструватися», для користувача — його ім'я з
  меню «Вийти» і «Видалити акаунт»;
- сторінки `#/login` і `#/register`: ім'я користувача, пароль (і його підтвердження під час
  реєстрації), перемикач «Показати пароль», правильні `autocomplete` для менеджерів
  паролів. Форма перевіряє ті самі правила, що й бекенд, ще до відправки, і показує помилки
  під полями; помилки сервера (неправильне ім'я чи пароль, зайняте ім'я, блокування після
  невдалих спроб або загальний ліміт запитів — кожне з кількістю секунд, задовгі дані) —
  українською над кнопкою. Ім'я обмежено 32 символами, паролі — 128 (`maxlength`). Після
  відправки поля пароля очищаються; після входу інтерфейс повертається на сторінку, з
  якої прийшов гість;
- гість може аналізувати знімки, а під результатом бачить примітку «Результат не збережено.
  Увійдіть, щоб зберігати історію.»; замість історії й статистики — пояснення з кнопками
  входу й реєстрації. Примітка залежить від того, чи був вхід у момент аналізу: якщо гість
  потім увійде, під тим самим результатом буде «Результат не збережено: аналіз виконано без
  входу.», а не неправдива причина;
- якщо сесія закінчилася, будь-яка відповідь 401 переводить інтерфейс у режим гостя з
  повідомленням «Сеанс завершився. Увійдіть знову.», а сторінка аналізу забуває останній
  знімок і результат (як після виходу: наступна людина за цим браузером їх не побачить);
  для аналізу — «Сеанс завершився, результат не збережено. Спробуйте ще раз.» (знімок
  лишається, наступна спроба вже анонімна);
- «Вийти» завершує сесію на сервері, повертає на головну й забуває історію та останній
  результат аналізу; «Видалити акаунт» відкриває діалог із попередженням і полем пароля.

Сесія існує лише в HttpOnly-cookie: інтерфейс нічого не зберігає в `localStorage` чи
`sessionStorage` (там лише вибрана тема), а паролі живуть тільки в стані форми. Якщо
`GET /auth/me` під час завантаження не вдався з іншої причини, ніж 401 (429, 503, немає
з'єднання), інтерфейс не робить користувача гостем: шапка не показує ні входу, ні імені,
історія запитується як звичайно (cookie може бути чинною), а `/auth/me` питається знову
через `Retry-After` або через 5, 10, 20… секунд (до хвилини). Виняток — бекенд без бази
(`DATABASE_URL` не задано, код `database_not_configured`): облікових записів тоді немає
взагалі, тож інтерфейс одразу показує гостя й більше не питає.

Помилки, які інтерфейс має розрізняти, він розпізнає за полем `code` відповіді, а не за
текстом `detail` (див. «Помилки» в розділі API).

Загальне: індикатор стану сервісу (перевіряє `/health` кожні 15 секунд), світла й темна
теми (вибір запам'ятовується, а за замовчуванням береться з налаштувань системи).
Сторінки перемикаються через адресу (`#/history`), тож працюють оновлення сторінки й кнопка
«Назад». Вибраний знімок і результат аналізу не губляться, поки відкрита історія.

## Налаштування

### Бекенд

Бекенд читає змінні середовища; їх також можна записати у файл `backend/.env` (шаблон —
`backend/.env.example`). Відносні шляхи рахуються від теки, з якої запущено `uvicorn`,
тобто від `backend/`.

| Змінна | Типове значення | Що означає |
|---|---|---|
| `MODEL_PATH` | `models/resnet18_v2c_best.pt` | Шлях до файлу ваг |
| `MODEL_VERSION` | `resnet18_v2c` | Назва ваг із `MODEL_PATH`; повертається в `/health` і `/predict` і зберігається в історії. Змінюйте разом із `MODEL_PATH` |
| `DEVICE` | `cpu` | Пристрій для обчислень: `cpu` або `cuda` |
| `MAX_UPLOAD_MB` | `10` | Найбільший розмір файлу, МБ |
| `MAX_PIXELS` | `16777216` | Найбільша кількість пікселів у знімку (ширина × висота); типове значення відповідає 4096 × 4096 |
| `MAX_IMAGE_SIDE` | `4096` | Найбільша довша сторона знімка, пікселів. Знімок доповнюється до квадрата зі стороною, що дорівнює довшій стороні, тому без цієї межі вузький знімок (наприклад, 16384 × 1024) у межах `MAX_PIXELS` потребував би сотні мегабайтів пам'яті |
| `MAX_CONCURRENT_INFERENCES` | `2` | Скільки прогнозів може виконуватися одночасно |
| `MAX_QUEUE` | `20` | Скільки запитів `/predict` може чекати на вільне місце, поки виконуються `MAX_CONCURRENT_INFERENCES` прогнозів. Наступні отримують 503 із заголовком `Retry-After` |
| `LOW_CONFIDENCE_THRESHOLD` | `0.9` | Поріг від 0 до 1: якщо ймовірність передбаченого класу нижча, прогноз отримує попередження `low_confidence`. Порівнюється неокруглене значення |

## Автентифікація

### Схема доступу

| Хто | `POST /predict` | `GET /predictions`, `GET` і `DELETE /predictions/{id}`, `GET /stats` |
|---|---|---|
| анонім (без cookie сесії) | працює як і раніше, з тим самим лімітом за адресою; відповідь та сама, але `"id": null`: результат **не зберігається** | 401 |
| зареєстрований (є сесія) | результат зберігається в історії цього користувача (`user_id`), `id` повертається | лише власні записи; чужий `id` дає 404, як і неіснуючий (не 403, щоб не розкривати, що такий запис є) |

`/health`, `/health/ready`, `/docs`, `/redoc` і `/openapi.json` лишаються публічними (без
входу; `/health/ready` і документація — лише на порту API, не через nginx). Записи, збережені до
появи облікових записів (міграція `0005`), не мають власника (`user_id` = `NULL`) і не
показуються нікому; з бази вони не видаляються.

Якщо запит надсилає cookie, яка не відповідає жодній чинній сесії (сесія закінчилася, вихід
уже був, cookie підроблена), API відповідає 401 і видаляє cookie (`Max-Age=0`). Це стосується
й `/predict`: користувач, який думає, що увійшов, має дізнатися, що результат не зберігся б.
Наступний запит без cookie вже анонімний.

### Ендпоінти

| Запит | Тіло | Відповідь |
|---|---|---|
| `POST /auth/register` | `{"username", "password"}` | 201 і користувач; одразу створює сесію (`Set-Cookie`). 409, якщо ім'я зайняте, 422, якщо ім'я чи пароль не відповідають вимогам |
| `POST /auth/login` | `{"username", "password"}` | 200 і користувач; нова сесія. 401 — «Неправильне ім'я користувача або пароль.» (однаково для невідомого імені й неправильного пароля) |
| `POST /auth/logout` | — | 204; видаляє сесію на сервері й cookie. Без сесії теж 204 (ідемпотентний) |
| `GET /auth/me` | — | 200 і користувач або 401 |
| `DELETE /auth/me` | `{"password"}` | 204; видаляє користувача, усі його сесії й усі його записи історії. 403 — неправильний пароль |

Користувач у відповіді: `{"id": "…", "username": "Alice", "created_at": "…"}`.

**Ім'я:** 3–32 символи, лише латинські літери, цифри, `_`, `.` і `-`. Зберігається так, як
його ввели, але унікальне без урахування регістру: `Alice` і `alice` — одне ім'я, і ввійти
можна будь-яким написанням. **Пароль:** 10–128 символів, не такий самий, як ім'я (теж без
урахування регістру). Помилки валідації приходять у звичайному форматі
`{"detail": "текст"}` і ніколи не повторюють надісланого пароля.

Приклад з curl через інтерфейс на порту 8080 (`-c`/`-b` — файл cookie; для запитів, що
змінюють дані, з cookie обов'язковий заголовок `Origin`, див. нижче):

```powershell
$o = "Origin: http://localhost:8080"
'{"username": "alice", "password": "correct-horse-1"}' | Set-Content -Encoding ascii body.json
curl.exe -c jar.txt -H $o -H "Content-Type: application/json" --data-binary "@body.json" `
  http://localhost:8080/auth/register
curl.exe -b jar.txt http://localhost:8080/auth/me
curl.exe -b jar.txt -H $o -F "file=@scan.jpg" http://localhost:8080/predict
curl.exe -b jar.txt "http://localhost:8080/predictions?limit=5"
curl.exe -b jar.txt -c jar.txt -H $o -X POST http://localhost:8080/auth/logout
```

### Що зберігається

- `users`: `id` (UUID), `username`, `password_hash`, `created_at`. Пошти немає.
- `sessions`: `id` — SHA-256 від токена (сам токен у базі не зберігається, тож копія бази
  не дає робочих cookie), `user_id`, `created_at`, `expires_at`.
- `predictions.user_id` — власник запису.

Пароль зберігається лише як хеш **argon2id** (`argon2-cffi`, параметри бібліотеки за
замовчуванням: 64 МіБ, 3 проходи, 4 потоки). Хеш обчислюється в окремому потоці, а не в
циклі подій, і одночасно — не більше двох (кожен займає ≈ 0,1 с процесора і 64 МіБ, а `api`
обмежено 1500 МіБ). Під час входу хеш, зроблений зі старими параметрами, перераховується
(`check_needs_rehash`). Пароль і токен ніколи не потрапляють у журнал, у відповіді чи в
`repr` моделей; помилки бази теж не показують переданих їй значень (`hide_parameters`).

Видалення користувача видаляє його сесії й записи на рівні бази (`ON DELETE CASCADE`). На
PostgreSQL рядки фізично лишаються у файлах таблиць, доки їх не перепише `VACUUM`
(автоматичний чи `VACUUM FULL`), як і для будь-якого видаленого запису.

**Чого немає:** пошти, тож немає ні скидання забутого пароля, ні підтвердження пошти; немає
зміни пароля й імені, входу через сторонні сервіси, двофакторної автентифікації, ролей і
адміністратора. Забутий пароль означає втрачений доступ до історії.

### Сесія і cookie

Токен — 32 випадкові байти з `secrets` (43 символи base64url). Кожен вхід і кожна реєстрація
створюють нову сесію з новим токеном; токен, який браузер приніс із собою, ніколи не
приймається як новий (захист від session fixation), а сесію, яку він називав, вхід видаляє.
Під час кожного входу видаляються й усі прострочені сесії. Сесія діє `SESSION_TTL_HOURS`
від входу і не подовжується. Одночасно в користувача може бути не більше
`SESSION_MAX_PER_USER` (10) сесій: новий вхід понад цю кількість видаляє найстаріші, тож
браузер, у якому входили найдавніше, отримає 401 і має увійти знову.

```
Set-Cookie: brain_mri_session=<токен>; HttpOnly; Max-Age=604800; Path=/; SameSite=Lax
```

- `HttpOnly` — скрипти сторінки cookie не бачать;
- `SameSite=Lax` — браузер не надсилає cookie із запитами `POST`/`DELETE` зі сторінок інших
  сайтів;
- `Secure` — лише з `SESSION_COOKIE_SECURE=true` (типово ні, бо HTTP на `localhost`);
- без `Domain`: cookie належить лише тому хосту, який її встановив.

### Захист від CSRF і перевірка Origin

Наявна перевірка `Origin` відхиляє `POST`/`PUT`/`PATCH`/`DELETE`, чий `Origin` не входить до
`ALLOWED_ORIGINS`, але пропускає запити без `Origin` (curl, скрипти). Автентифікація додає
одне правило: **якщо запит, що змінює дані, надсилає cookie сесії, `Origin` обов'язковий** і
має бути з `ALLOWED_ORIGINS`, інакше 403 з поясненням.

| `Origin` | Без cookie сесії | З cookie сесії |
|---|---|---|
| з `ALLOWED_ORIGINS` | пропускається | пропускається |
| інший (зокрема `null`) | 403 | 403 |
| відсутній | пропускається (curl, скрипти: від імені користувача вони нічого не змінять) | **403** (нове) |

Читання (`GET`) з cookie `Origin` не потребує. Від сторінок інших сайтів його захищає
перевірка `Sec-Fetch-Site` (див. «Rate limiting»), а `SameSite=Lax` не дає cookie для
вбудованих запитів між сайтами. `SameSite` сам по собі не досить: сторінки на інших портах
того самого хоста (`localhost:5173` і `localhost:8080`) для браузера — один «сайт», і cookie
з ними надсилається; захищає саме `Origin`. Браузер додає `Origin` до кожного `POST` і
`DELETE`, тож інтерфейс, Swagger UI і проксі Vite працюють без змін; curl із файлом cookie
має додати `-H "Origin: http://localhost:8080"`.

### Ліміти

- Вхід і реєстрація (`POST /auth/login`, `POST /auth/register`) мають окремий суворий ліміт:
  `RATE_LIMIT_AUTH_PER_MINUTE` (типово 10) запитів за адресою за 60 секунд. `GET /auth/me`
  інтерфейс викликає під час кожного завантаження сторінки, тож він рахується як звичайне
  читання (120 за хвилину) і не відбирає спроб входу; навіть після 429 на вході `GET
  /auth/me` відповідає. `POST /auth/logout` і `DELETE /auth/me` рахуються як зміна даних
  (30 за хвилину).
- Не більше `LOGIN_FAILURES_MAX` (5) неправильних паролів за `LOGIN_FAILURES_WINDOW_MINUTES`
  (15 хвилин) на пару «ім'я (без урахування регістру), адреса»: далі 429 із `Retry-After`
  (секунди, доки найстаріша невдача не вийде з вікна), навіть із правильним паролем, і пароль
  тоді не перевіряється. Невідомі імена рахуються так само, тож ліміт не видає, які імена
  існують. Успішний вхід обнуляє лічильник. Неправильний пароль у `DELETE /auth/me` теж
  рахується. Інше ім'я з тієї самої адреси чи те саме ім'я з іншої адреси не блокуються.
  Лічильник — у пам'яті процесу, як і решта лімітів (див. «Rate limiting»), і діє незалежно
  від `RATE_LIMIT_ENABLED`. Пам'ять він займає так само обмежену: не більше 10 000 пар «ім'я,
  адреса»; коли їх більше, за O(1) забувається пара, що найдовше не мала невдач. Тому
  зловмисник, який перебирає 10 000 різних імен, може «стерти» лічильник для чужого імені,
  але з однієї адреси ліміт входу й реєстрації дозволяє на це щонайменше 1000 хвилин.
- Тіло запиту до `/auth/*` — не більше 8 КіБ (ім'я й пароль уміщаються з великим запасом).
  Більше тіло отримує 413 у звичайному форматі помилки (`{"detail": "Тіло запиту до /auth/*
  завелике: дозволено не більше 8 КіБ."}`) ще до того, як його дочитано до кінця, а тим
  паче розібрано як JSON; для тіла без `Content-Length` байти рахуються під час читання.
- Під Docker Desktop усі клієнти цього комп'ютера приходять з однієї адреси (шлюз мережі
  Docker, див. «Rate limiting»). Тому п'ять неправильних паролів для імені з будь-якої
  програми на ньому блокують вхід під цим ім'ям для всіх локальних клієнтів на 15 хвилин, а
  ліміт входу й реєстрації (10 за хвилину) вони теж ділять.

### Порядок перевірок

`Host` (400) → `Origin`, зокрема обов'язковий `Origin` для запису з cookie (403) →
`Sec-Fetch-Site` (403) → ліміт частоти (429) → сесія (401; 503 без бази) → тіло запиту
(413, 422, 400…). Тому запит без чинної сесії відхиляється до того, як прочитано файл чи
JSON, а відхилені на ранніх кроках запити не витрачають ліміт. Ліміт невдалих входів
перевіряється вже після читання тіла: йому потрібне ім'я.

### Відповіді не кешуються

`Cache-Control: no-store` мають усі відповіді `/auth/*`, історії (`/predictions`,
`/predictions/{id}`, `/stats`) і будь-яка відповідь на запит із cookie сесії (зокрема
`/predict` зареєстрованого користувача). Анонімний `/predict` і `/health` — без змін.

## Історія прогнозів

### Що зберігається

Після кожного успішного `POST /predict` **із сесією** у таблицю `predictions` додається запис
із `user_id` цього користувача, а його `id` повертається у відповіді. Анонімні прогнози й
невдалі запити (400, 413, 415, 422) не зберігаються.

Знімок, назва файлу та його хеш **не зберігаються** (про тимчасовий файл на час запиту див.
на початку README). До міграції `0004` у базі лежав SHA-256 файлу (`image_sha256`), але його
ніщо не читало, а маючи файл, за хешем можна було б перевірити, чи цей знімок аналізували.
Тому стовпець видалено. Як прибрати старі значення з диска, див. «Міграції».

### Схема таблиці `predictions`

| Стовпець | Тип у Postgres | Зміст |
|---|---|---|
| `id` | `uuid`, первинний ключ | Ідентифікатор запису |
| `created_at` | `timestamp with time zone` | Час прогнозу (UTC) |
| `predicted_class` | `varchar(20)` | Передбачений клас; дозволено лише чотири класи |
| `probabilities` | `jsonb` | Ймовірності чотирьох класів |
| `image_width`, `image_height` | `integer` | Розмір знімка в пікселях (більше 0) |
| `warnings` | `jsonb` | Список попереджень (`code`, `message`). Обмеження `ck_predictions_warnings_is_array` (міграція `0003`) дозволяє зберігати тут лише JSON-масив |
| `gradcam_requested` | `boolean` | Чи запитували теплову карту |
| `latency_ms` | `double precision` | Час обробки запиту без збереження в історію, мс. Включає обчислення ознак `not_mri_like` (≈ +6 мс для 512 × 512, до ≈ +0,3 с для 4096 × 4096); у записах, збережених до появи цього попередження, цього часу немає |
| `model_version` | `varchar(64)` | Версія моделі (`MODEL_VERSION`), що зробила прогноз. Записи, збережені до міграції `0002`, отримали `resnet18_v2`; нові записи мають вказувати версію явно |
| `user_id` | `uuid`, може бути `NULL`, зовнішній ключ на `users.id` з `ON DELETE CASCADE` | Власник запису. `NULL` — записи, збережені до міграції `0005`: їх не бачить ніхто |

Індекси: `created_at`, `predicted_class`, `(user_id, created_at)` — для історії одного
користувача від найновішого запису.

Таблиці облікових записів (міграція `0005`):

| Таблиця | Стовпці | Обмеження й індекси |
|---|---|---|
| `users` | `id` (`uuid`), `username` (`varchar(32)`), `password_hash` (`varchar(255)`, argon2id), `created_at` | унікальний індекс `uq_users_username_lower` на `lower(username)` |
| `sessions` | `id` (`varchar(64)`, SHA-256 токена), `user_id` (`uuid`), `created_at`, `expires_at` | `user_id` → `users.id` з `ON DELETE CASCADE`; індекси `user_id`, `expires_at` |

### Міграції

Схема бази ведеться міграціями Alembic у `backend/migrations/`. Адресу бази Alembic бере з
тієї самої змінної `DATABASE_URL`, що й сервіс. Команди виконуються з теки `backend/`:

```powershell
alembic upgrade head                                   # оновити базу до останньої версії
alembic current                                        # поточна версія бази
alembic check                                          # чи збігаються моделі й міграції
alembic revision --autogenerate -m "опис змін"         # нова міграція після зміни records.py
alembic downgrade -1                                   # відкотити останню міграцію
```

Створену автоматично міграцію варто переглянути перед комітом. У Docker Compose
`alembic upgrade head` виконується автоматично перед кожним стартом `api`.

Міграція `0003` додає на Postgres обмеження `CHECK (jsonb_typeof(warnings) = 'array')`.
Спершу вона перевіряє наявні записи: якщо в якомусь `warnings` не масив, міграція
зупиняється, нічого не змінивши, і виводить `id` таких записів (до 20) та їхні значення.
Виправте або видаліть ці записи вручну й запустіть міграцію знову. На SQLite, де немає
`jsonb_typeof`, обмеження не додається.

Міграція `0004` видаляє стовпець `image_sha256` і його індекс зі схеми. Але на PostgreSQL
`DROP COLUMN` лише позначає стовпець видаленим: старі значення лишаються у файлах таблиці,
доки її не буде переписано. Тому після міграції рекомендовано один раз виконати
`VACUUM FULL predictions`, наприклад у Docker Compose (користувач і база — значення
`POSTGRES_USER` і `POSTGRES_DB` з `.env`):

```powershell
docker compose exec db psql -U brain_mri -d brain_mri -c "VACUUM FULL predictions;"
```

Команда переписує таблицю вже без значень видаленого стовпця; на час виконання таблиця
заблокована (для невеликої історії це частки секунди). Резервні копії бази, зроблені до
міграції, хеші містять. `alembic downgrade 0003` повертає стовпець і індекс, але вже як
необов'язковий (`NULL`): старі значення він не відновлює. Хеші в цьому проєкті стосувалися
лише знімків із датасету та тестових файлів: реальних пацієнтів у проєкті немає.

**Код і міграцію `0004` розгортайте разом: спершу `alembic upgrade head`, потім новий код.**
У Docker Compose так і відбувається перед кожним стартом `api`. Код після `0004` уже не
пише `image_sha256`, а база до неї вимагає цей стовпець, тож якщо запустити новий код до
міграції (наприклад, `uvicorn --reload` у розробці), кожне збереження в історію не вдасться.
Навпаки, відкат коду на версію до `0004` без `alembic downgrade 0003` теж ламає збереження:
старий код пише в стовпець, якого вже немає. В обох випадках прогнози повертаються, але з
`"id": null`, а причину видно лише в журналі.

Міграція `0005` створює таблиці `users` і `sessions` і додає до `predictions` стовпець
`user_id` із зовнішнім ключем та індексом. Наявні записи лишаються на місці з
`user_id` = `NULL`: їх не показують нікому, але й не видаляють. Перед міграцією варто
зробити копію бази (так робилося й перед `0003` та `0004`):

```powershell
docker compose up -d db
docker compose exec db pg_dump -U brain_mri -d brain_mri -Fc -f /tmp/before_0005.dump
docker compose cp db:/tmp/before_0005.dump ..\brain_mri_before_0005.dump
docker compose exec db rm /tmp/before_0005.dump
```

Дамп робиться всередині контейнера й копіюється `docker compose cp` (тут — у теку поза
репозиторієм), а не перенаправленням `>` у PowerShell: воно перекодовує двійковий вивід
`pg_dump` і псує файл.

`alembic downgrade 0004` видаляє таблиці `users` і `sessions` і стовпець `user_id`, але
лишає всі записи історії: їхні власники забуваються. Код до `0005` показує всю історію
будь-кому, тож після такого відкату записи всіх користувачів стануть видимі всім, хто має
доступ до API; міграція пише в журнал, скільки записів втратили власника. Як і з `0004`,
розгортайте код і міграцію разом: код після `0005` читає й пише `user_id`.

Якщо запис усе ж має пошкоджені попередження (не список, елементи без текстових `code` і
`message`), історія однаково відкривається: такі попередження пропускаються, у журнал
іде повідомлення з `id` запису, а решта полів повертається як звичайно. `/stats` рахує
лише коректні попередження.

### Якщо база недоступна

Прогноз однаково повертається, але з `"id": null`, а помилка записується в журнал. Для
запиту з cookie сесії API не може перевірити сесію, тож виконує прогноз як анонімний: він
не зберігся б однаково. Щоб кожен прогноз не чекав на недоступну базу кілька секунд, після
помилки з'єднання (або коли за відведений час не звільнилося з'єднання в пулі) сервіс 30
секунд не звертається до неї ні для перевірки сесії в `/predict`, ні для збереження: такі
прогнози теж не зберігаються, а в журнал іде попередження. Ендпоінти історії, `/auth/me`,
вхід і реєстрація тим часом відповідають 503, як і `/health/ready` (`"database": false`), а
`/health` — 200. Коли база повертається, збереження
відновлюється само. Якщо ж база працює, але відхилила один запис (наприклад, через
обмеження таблиці), не зберігається лише він: паузи немає.

## Типи API

Типи TypeScript для запитів і відповідей генеруються з OpenAPI-схеми FastAPI пакетом
`openapi-typescript`. Згенерований файл `frontend/src/api/schema.d.ts` лежить у репозиторії,
тому для звичайної роботи генерувати його не потрібно.

Після зміни API бекенду запустіть бекенд (локально або через Docker Compose) і виконайте:

```powershell
cd frontend
npm run generate:api
```

Скрипт читає схему з <http://127.0.0.1:8000/openapi.json> і перезаписує `schema.d.ts`.
Закомітьте оновлений файл разом зі змінами бекенду. Короткі назви типів, якими
користується решта коду, оголошено у `frontend/src/api/types.ts`.

## Тести та перевірки

**Бекенд** (з активованим середовищем):

```powershell
cd backend
pytest
```

Тести не потребують ні справжніх ваг, ні Postgres. Модель у них — ResNet18 із випадковими
вагами (один вихід посилено, щоб модель була впевненою і попередження `low_confidence`
з'являлося лише в тестах, які його перевіряють), а історія зберігається в SQLite у пам'яті. Тести покривають збереження прогнозів,
пагінацію, фільтр, видалення, `/stats`, роботу без `DATABASE_URL` і з недоступною базою,
поріг попередження `low_confidence`, ознаки й пороги попередження `not_mri_like` (на
синтетичних зображеннях: шум, суцільні й кольорові кадри, схожий на знімок сірий кадр),
а також міграції: їхню відповідність моделям і
заповнення `model_version` для старих записів, видалення й відновлення `image_sha256` (міграція
`0004` вгору й униз на SQLite), таблиці облікових записів і `user_id` (міграція `0005` вгору
й униз на таблиці з наявними записами, каскадне видалення). Автентифікацію перевіряють
`test_auth.py` (реєстрація, вхід, cookie, прострочення й підробка сесії, вихід, видалення
облікового запису, CSRF, `no-store`, відсутність пароля й токена в журналі),
`test_history_access.py` (кожен бачить лише свої записи) і `test_rate_limit.py` (ліміти
`/auth/*` і невдалих входів). `test_health.py` перевіряє liveness і readiness: 503 без
моделі чи бази (базу підміняє рушій, що кидає виняток або зависає), відсутність тексту
помилки у відповіді, 2-секундний таймаут, окремий рушій перевірки (заповнений спільний
пул їй не заважає) і його ліміти часу (зокрема keepalive), кеш на 2 с, одну живу перевірку
(зависла не дає запустити нову, а після її завершення нова стартує; запити, що чекають на
неї, не додають їй зворотних викликів), відсутність хибних записів у журналі,
зупинку без очікування завислої перевірки й без блокування циклу подій, а також те, що
обидва шляхи не обмежуються лімітом, не проходять перевірку `Sec-Fetch-Site` і не
потребують сесії. Один тест запускає локальний TCP-сервер, що мовчить, замість Postgres
(межа підключення). Повністю прогнати тести на Linux можна в образі бекенду (див. нижче).
`test_deployment.py` перевіряє файли розгортання, зокрема healthcheck `api` на
`/health/ready`, відповідь 404 на цей шлях у `nginx.conf` і те, що проксі Vite його не
пересилає. Паролі в них хешуються справжнім argon2id. Один тест додатково перевіряє справжні ваги,
якщо файл `backend/models/resnet18_v2c_best.pt` є на місці, а інакше пропускається.

Усі тести бекенду на Linux, в образі `api` (зібраному `docker compose build api`; репозиторій
монтується лише для читання, тести з `docker compose config` там пропускаються):

```powershell
docker run --rm -u root -e PYTHONDONTWRITEBYTECODE=1 -v "${PWD}:/repo:ro" -w /repo/backend `
  brain-mri-service-api sh -c "pip install -q -r requirements-dev.txt && python -m pytest -q -p no:cacheprovider"
```

**Вебінтерфейс:**

```powershell
cd frontend
npm test              # Vitest + React Testing Library, один прогін
npm run test:watch    # перезапуск тестів після змін
npm run typecheck     # перевірка типів TypeScript
npm run lint          # ESLint
npm run format:check  # Prettier; npm run format виправляє форматування
```

Тести вебінтерфейсу не звертаються до бекенду: `fetch` у них замокано. Вони перевіряють
сторінку аналізу (перевірку файлу, успішну відповідь, попередження, помилки), сторінку
історії (статистику, таблицю, пагінацію, фільтр, видалення, помилки 404 і 503),
перемикання сторінок і теми, а також вхід, реєстрацію й вихід: валідацію форм, помилки
401/409/422/429, вигляд для гостя й користувача, обробку закінченої сесії в одному місці
(`client.ts`), видалення акаунта й те, що в `localStorage` і `sessionStorage` нічого не
з'являється.

Якщо на комп'ютері мало вільної пам'яті (наприклад, поруч працює Docker), Vitest може
впасти з `JavaScript heap out of memory`. Тоді запустіть тести в одному процесі:
`npx vitest run --maxWorkers=1`.

## Rate limiting

API обмежує, скільки запитів один клієнт може надіслати за будь-які 60 секунд (ковзне вікно).
Ліміти окремі для чотирьох видів запитів:

| Вид | Запити | Типовий ліміт |
|---|---|---|
| аналіз | `POST /predict` | 10 (`RATE_LIMIT_PREDICT_PER_MINUTE`) |
| зміна даних | `DELETE /predictions/{id}`, `POST /auth/logout`, `DELETE /auth/me` | 30 (`RATE_LIMIT_WRITE_PER_MINUTE`) |
| читання | `GET` історії, статистики, документації й `GET /auth/me` | 120 (`RATE_LIMIT_READ_PER_MINUTE`) |
| вхід і реєстрація | `POST /auth/login`, `POST /auth/register` | 10 (`RATE_LIMIT_AUTH_PER_MINUTE`) |

Окремо від цих лімітів рахуються невдалі входи: не більше 5 неправильних паролів за 15
хвилин на пару «ім'я, адреса» (див. «Автентифікація»). Ліміти рахуються за адресою, а не
за користувачем, і для зареєстрованих теж: ліміт перевіряється до сесії, якій потрібна
база.

`/health` і `/health/ready` не обмежуються: на них звертаються healthcheck-и контейнерів. Вимкнути
обмеження можна змінною `RATE_LIMIT_ENABLED=false`.

Понад ліміт API відповідає `429` у звичайному форматі помилки, із заголовком `Retry-After`
(ціле число секунд, не менше 1) і всіма заголовками безпеки:

```json
{"detail": "Забагато запитів. Спробуйте ще раз через 42 с."}
```

Інтерфейс показує повідомлення із заголовком «Забагато запитів» і текстом «Спробуйте ще раз
через N с.» (без заголовка `Retry-After` — «Спробуйте ще раз трохи згодом.»).

**Порядок перевірок.** Спершу `Host` (400), `Origin` (403) і перевірка міжсайтових запитів
(403, див. нижче): відхилені ними запити ліміту не витрачають. Потім ліміт, потім сесія (401,
див. «Автентифікація»), і лише після цього читається тіло запиту. Тому рахуються всі спроби `/predict`, зокрема з файлом, який потім
буде відхилено з кодом 400, 413 чи 415, а запит, відхилений лімітом, не доходить ні до
моделі, ні до черги інференсу. `503` від переповненої черги (`MAX_QUEUE`) лишається окремою
відповіддю зі своїм `Retry-After`.

**Запити зі сторінок інших сайтів.** Перевірка `Origin` стосується лише запитів, що змінюють
дані, тож без додаткового захисту будь-яка сторінка, відкрита в браузері, могла б вичерпати
ліміт читання, наприклад підвантажуючи `<img src="http://localhost:8080/stats">`. Під Docker
Desktop усі локальні клієнти ділять один ліміт, тож справжній інтерфейс отримував би 429.
Тому API відповідає 403 у звичайному форматі помилки
(`{"detail": "Запити зі сторінок інших сайтів заборонено. Дозволені джерела задає
ALLOWED_ORIGINS."}`) на будь-який запит, крім `/health` і `/health/ready`, у якого
заголовок браузера
`Sec-Fetch-Site` дорівнює `cross-site` чи `same-site`, а `Origin` відсутній або не входить до
`ALLOWED_ORIGINS`. Такий запит не витрачає ліміт і не доходить до моделі. Проходять:
`same-origin` (власний інтерфейс), `none` (адресу введено вручну) і запити без
`Sec-Fetch-Site` (curl, скрипти, серверні клієнти). nginx передає заголовки `Sec-Fetch-*` без
змін; тест деплою стежить, щоб так і лишалося.

**Хто такий клієнт.** Ключ ліміту — адреса клієнта; її визначає окрема функція
(`rate_limit_key` у `backend/app/rate_limit.py`). Адреса — це співрозмовник TCP-з'єднання. Заголовку `X-Real-IP` API
вірить лише тоді, коли з'єднання прийшло з адреси, переліченої в `TRUSTED_PROXIES`;
від усіх інших підроблений заголовок ігнорується. nginx перезаписує `X-Real-IP` адресою,
яку бачить сам, тож клієнт не може підставити чужу і через порт 8080. Якщо від довіреного
проксі прийшов некоректний заголовок, запит рахується за адресою самого проксі. Клієнти
IPv6 групуються за префіксом `/64`, бо такий блок зазвичай належить одному абоненту.
Адреси клієнтів у базу не записуються: лічильники живуть лише в пам'яті процесу.

**Пам'ять.** Для кожного клієнта зберігається не більше «ліміт» міток часу прийнятих
запитів (відхилені не зберігаються), клієнти без запитів за останню хвилину прибираються, а
всього на кожен вид запитів відстежується не більше 10 000 клієнтів; якщо їх більше,
забувається той, хто довше за всіх не надсилав запитів.

**Обмеження цього підходу.**

- Стан — у пам'яті одного процесу. Якщо запустити кілька воркерів uvicorn або кілька
  контейнерів API, кожен рахуватиме окремо, і реальний ліміт помножиться на їхню
  кількість; для цього потрібне спільне сховище (наприклад, Redis). Після перезапуску API
  лічильники обнуляються.
- Під Docker Desktop усі запити з цього комп'ютера приходять з однієї адреси — шлюзу
  мережі Docker `172.30.250.128` — і через nginx, і напряму на порт 8000. Тому всі
  локальні клієнти (кілька браузерів, curl, скрипти) ділять один ліміт, а ліміт, вичерпаний
  через 8080, діє й на прямі запити до 8000. Окремі клієнти розрізняються лише тоді, коли
  до nginx звертаються з різних адрес (наприклад, з інших машин).
- Обмеження діє лише на рівні API: nginx сам частоту запитів не обмежує, а статичні файли
  інтерфейсу не обмежуються взагалі.
- Відповіді `503` від переповненої черги теж рахуються в ліміт `/predict`. Клієнт, який
  повторює запит кожні 5 секунд, як радить `Retry-After`, на 11-й спробі за хвилину отримає
  429. Це навмисно: повтори на перевантажений сервіс теж обмежуються.
- Шлях порівнюється повністю. Якщо запустити uvicorn з `--root-path` (зараз так не
  робиться), `/api/predict` потрапить у ліміт зміни даних, а не аналізу, а `/api/health` і
  `/api/health/ready` теж обмежуватимуться.
- Потрібне TCP-з'єднання з адресою. Якщо проксі підключається до API через Unix-сокет,
  адреси в з'єднання немає: усі клієнти отримують спільний ключ `unknown`, а `X-Real-IP`
  не може бути довіреним, бо `TRUSTED_PROXIES` приймає лише IP-адреси.

## API

### `GET /health`

Liveness (див. «Перевірки стану: liveness і readiness»). Повертає стан сервісу, пристрій,
класи в порядку виходів моделі і версію моделі. Від бази не залежить і відповідає одразу, навіть коли сервер зайнятий прогнозами: запити до
`/predict` чекають своєї черги, не займаючи потоків, якими користуються інші ендпоінти.

```json
{
  "status": "ok",
  "device": "cpu",
  "classes": ["glioma", "meningioma", "notumor", "pituitary"],
  "model_version": "resnet18_v2c"
}
```

### `GET /health/ready`

Readiness: 200, коли модель завантажена, а база відповіла на `SELECT 1` за 2 секунди,
інакше 503. Без `DATABASE_URL` база не перевіряється (`"database": null`), і відповідь
залежить лише від моделі. Відповідь не кешується (`Cache-Control: no-store`). Доступний
лише на порту API (8000) і всередині Compose; через nginx (8080) — 404.

```json
{"status": "ready", "model": true, "database": true}
```

```json
{"status": "not_ready", "model": true, "database": false}
```

```json
{"status": "ready", "model": true, "database": null}
```

### `POST /predict`

Знімок передається у полі `file` запиту `multipart/form-data`. Параметр `gradcam=true`
додає до відповіді теплову карту. Сесія не обов'язкова: без неї прогноз повертається, але
не зберігається (`"id": null`); із сесією він зберігається в історії користувача (див.
«Автентифікація»). Приклади нижче — анонімні.

Одночасно виконується не більше `MAX_CONCURRENT_INFERENCES` прогнозів (типово 2). Інші
запити чекають у черзі довжиною до `MAX_QUEUE` (типово 20), а якщо й вона заповнена,
сервер одразу відповідає 503 із заголовком `Retry-After: 5`.

```powershell
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict"
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true"
```

Приклад відповіді для знімка 640 × 480 без теплової карти:

```json
{
  "id": "43eb20d2-5203-42e7-8903-a86a82a76fbf",
  "predicted_class": "meningioma",
  "probabilities": {
    "glioma": 0.0012,
    "meningioma": 0.9988,
    "notumor": 0.00004,
    "pituitary": 0.0000001
  },
  "image_size": {"width": 640, "height": 480},
  "warnings": [
    {
      "code": "unexpected_image_size",
      "message": "Розмір знімка відрізняється від 512×512. Для гліом такого формату recall у перевірці був ≈ 0,51 (проти ≈ 0,99 для 512×512): якщо є підозра на гліому, результат менш надійний."
    }
  ],
  "gradcam_png_base64": null,
  "model_version": "resnet18_v2c"
}
```

| Поле | Зміст |
|---|---|
| `id` | Ідентифікатор запису в історії; `null`, якщо історію вимкнено або запис не вдалося зберегти |
| `predicted_class` | Клас із найбільшою ймовірністю |
| `probabilities` | Ймовірності чотирьох класів; у сумі дають 1 |
| `image_size` | Розмір завантаженого знімка в пікселях |
| `warnings` | Список попереджень (`code`, `message`); порожній список, якщо попереджень немає. Коди: `not_mri_like` — зображення не схоже на знімок МРТ (див. нижче), завжди йде першим; `unexpected_image_size` — розмір знімка не 512 × 512; `low_confidence` — ймовірність передбаченого класу нижча за `LOW_CONFIDENCE_THRESHOLD` |
| `gradcam_png_base64` | Теплова карта у форматі PNG, закодована в base64; `null`, якщо її не просили |
| `model_version` | Версія моделі, що зробила прогноз (`MODEL_VERSION`) |

**Попередження `not_mri_like`.** Модель упевнено класифікує будь-яке зображення, зокрема
шум чи фото. Тому сервіс рахує на декодованому знімку в його власній роздільності чотири
прості ознаки, а також частку непрозорих пікселів файлу, і додає попередження, якщо
виконується хоча б одна умова (усі порівняння строгі: значення, що дорівнює порогу,
попередження не дає):

- кольоровість (середнє по пікселях `max(|R−G|, |G−B|, |R−B|)`) більша за `NOT_MRI_COLOR_MAX` (7);
- шумність (середній модуль різниці сусідніх пікселів, поділений на стандартне відхилення
  яскравості) більша за `NOT_MRI_NOISE_MAX` (0,85);
- стандартне відхилення яскравості менше за `NOT_MRI_STD_MIN` (10): майже однорідний кадр.
  Для суцільного кадру (відхилення 0) шумність не визначена, і спрацьовує саме ця умова;
- стандартне відхилення менше за `NOT_MRI_LOWCONTRAST_STD` (30) **і** частка темних пікселів
  (яскравість нижче 10 % шкали) менша за `NOT_MRI_DARK_MIN` (0,15): тьмяне зображення без
  темного фону, який має кожен знімок;
- частка повністю непрозорих пікселів менша за `NOT_MRI_OPAQUE_MIN` (0,99). Сервіс малює
  прозорі пікселі чорними, і без цієї умови прозорі поля ставали б фальшивим темним фоном:
  тьмяний шум зі смугами прозорості по 60 пікселів з боків проходив би решту перевірок. У
  датасеті прозорості немає: альфа-канал мають лише 3 файли з 7200, і в них непрозорі всі
  пікселі.

Це попередження, а не відмова: прогноз повертається як завжди. На 7200 знімках датасету
Kaggle найбільша кольоровість 5,66, найбільша шумність 0,62, найменше відхилення 20,8, а
умову низького контрасту не виконує жоден знімок. Тобто жоден знімок попередження не
отримує, а всі 16 перевірених зразків отримують: шум, суцільні кадри, 8 кольорових фото,
знімок екрана. Межі методу див. в «Обмеженнях».

Ознаки рахуються смугами по 512 рядків через гістограми Pillow. Суми цілі, тож результат
точний, а повної копії зображення не створюється. На машині розробника (Windows, CPU) це
займає ≈ 6 мс для 512 × 512 (сам прогноз моделі ≈ 40 мс) і ≈ 0,3 с та ≈ 30 МіБ пам'яті
для найбільшого допустимого 4096 × 4096 (прогноз моделі ≈ 0,2 с). У сірих файлах (режими
`L`, `LA`, `1`; таких 3067 із 7200 знімків датасету) кольору немає, тож він не рахується:
сірий 4096 × 4096 займає ≈ 0,12 с.

Приклад відповіді для зображення 512 × 512 із випадковим шумом: модель майже впевнена, що
пухлини немає, і лише попередження каже, що це не знімок:

```json
{
  "id": "0d6a3f8e-7c41-4b1e-9a52-3e8f2b9c1d70",
  "predicted_class": "notumor",
  "probabilities": {
    "glioma": 0.0028,
    "meningioma": 0.0012,
    "notumor": 0.9928,
    "pituitary": 0.0033
  },
  "image_size": {"width": 512, "height": 512},
  "warnings": [
    {
      "code": "not_mri_like",
      "message": "Зображення не схоже на знімок МРТ (кольорове, шумне, однорідне або без темного фону). Результат не можна вважати достовірним."
    }
  ],
  "gradcam_png_base64": null,
  "model_version": "resnet18_v2c"
}
```

Зберегти теплову карту у файл можна так:

```powershell
$r = curl.exe -s -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true" | ConvertFrom-Json
[IO.File]::WriteAllBytes("$PWD\gradcam.png", [Convert]::FromBase64String($r.gradcam_png_base64))
```

### `GET /predictions`

Сторінка історії поточного користувача, від найновішого запису. Цей і три наступні
ендпоінти потребують сесії (без неї — 401) і бачать лише записи цього користувача.

| Параметр | Типово | Що означає |
|---|---|---|
| `limit` | `20` | Скільки записів повернути (1–100) |
| `offset` | `0` | Скільки записів пропустити (0–1 000 000) |
| `predicted_class` | — | Лише прогнози цього класу |

```powershell
curl.exe -b jar.txt "http://localhost:8080/predictions?limit=10&offset=0&predicted_class=glioma"
```

```json
{
  "items": [
    {
      "id": "43eb20d2-5203-42e7-8903-a86a82a76fbf",
      "created_at": "2026-11-12T21:42:29.815061Z",
      "predicted_class": "glioma",
      "probabilities": {"glioma": 0.91, "meningioma": 0.05, "notumor": 0.03, "pituitary": 0.01},
      "image_size": {"width": 512, "height": 512},
      "warnings": [],
      "gradcam_requested": true,
      "latency_ms": 224.7,
      "model_version": "resnet18_v2c"
    }
  ],
  "total": 1,
  "limit": 10,
  "offset": 0
}
```

`total` — кількість усіх записів користувача, що відповідають фільтру, а не лише цієї
сторінки.

### `GET /predictions/{id}`

Один запис у тому самому форматі, що й елемент `items`. Якщо в цього користувача такого
запису немає — 404; чужий запис і запис без власника теж дають 404.

### `DELETE /predictions/{id}`

Видаляє власний запис. Успіх — 204 без тіла; якщо в цього користувача такого запису немає
(зокрема якщо він чужий) — 404. Якщо той самий запис видаляють кілька запитів одночасно,
204 отримує лише один із них, решта — 404.

### `GET /stats`

```json
{
  "total": 3,
  "by_class": {"glioma": 0, "meningioma": 2, "notumor": 1, "pituitary": 0},
  "with_warnings_share": 0.3333,
  "average_latency_ms": 118.6,
  "warnings_by_code": {"unexpected_image_size": 1, "low_confidence": 0, "not_mri_like": 0}
}
```

Статистика лише прогнозів поточного користувача.

| Поле | Зміст |
|---|---|
| `total` | Кількість збережених прогнозів |
| `by_class` | Кількість прогнозів для кожного класу |
| `with_warnings_share` | Частка прогнозів із будь-яким попередженням (від 0 до 1); прогноз із кількома попередженнями рахується один раз |
| `average_latency_ms` | Середній час обробки, мс. Змішує записи до й після появи `not_mri_like`: новіші включають ще й обчислення його ознак (≈ +6 мс для 512 × 512, до ≈ +0,3 с для 4096 × 4096) |
| `warnings_by_code` | Кількість прогнозів із кожним кодом попередження. Прогноз із кількома попередженнями враховується в кожному з них, тому сума може перевищувати кількість прогнозів із попередженнями. `unexpected_image_size`, `low_confidence` і `not_mri_like` є завжди, навіть із 0; інші коди з'являються, коли трапляються |

Поки прогнозів немає, `with_warnings_share` і `average_latency_ms` дорівнюють `null`, а
`warnings_by_code` містить нулі. Поле `warnings_by_code` додано без зміни наявних полів.

Усі числа описують один момент, навіть якщо тим часом зберігаються нові прогнози:
кількості й середній час рахуються одним SQL-запитом (тому `total` завжди дорівнює сумі
`by_class`), а на Postgres обидва запити `/stats` виконуються в одній транзакції
`REPEATABLE READ`.

### Помилки

| Код | Коли виникає |
|---|---|
| 400 | Файл порожній, не є зображенням або пошкоджений; або заголовок `Host` не входить до `ALLOWED_HOSTS` (тоді тіло відповіді — текст `Invalid host header`) |
| 401 | Немає сесії (історія, `/auth/me`) або cookie сесії недійсна чи сесія закінчилася (історія, `/auth/me`, `/predict`; відповідь ще й видаляє cookie); для `POST /auth/login` — неправильне ім'я або пароль |
| 403 | `POST` або `DELETE` із заголовком `Origin`, якого немає в `ALLOWED_ORIGINS` (запит зі сторінки іншого сайту); `POST` або `DELETE` із cookie сесії, але без `Origin` (CSRF); будь-який запит, крім `/health` і `/health/ready`, із `Sec-Fetch-Site: cross-site` чи `same-site` без дозволеного `Origin` (див. «Rate limiting»); неправильний пароль у `DELETE /auth/me` |
| 404 | У цього користувача немає запису з таким `id` (чужий запис теж дає 404) |
| 409 | `POST /auth/register`: ім'я вже зайняте (без урахування регістру) |
| 413 | Файл більший за `MAX_UPLOAD_MB`, знімок має більше пікселів, ніж `MAX_PIXELS`, або його довша сторона більша за `MAX_IMAGE_SIDE`; тіло запиту до `/auth/*` більше за 8 КіБ |
| 415 | Зображення не у форматі JPEG чи PNG (наприклад, GIF, BMP, TIFF, WEBP), 16-бітне (зокрема 16-бітний PNG у відтінках сірого) або має кілька кадрів (анімований PNG) |
| 422 | Некоректний запит: немає поля `file`, неправильний `gradcam`, `limit`, `offset`, клас або `id`; тіло `/auth/*` не є JSON-об'єктом із потрібними текстовими полями; ім'я чи пароль під час реєстрації не відповідають вимогам; також якщо значення із запиту не прийняла сама база даних |
| 429 | Забагато запитів від цього клієнта за останні 60 секунд (див. «Rate limiting») або забагато неправильних паролів для цього імені з цієї адреси (див. «Автентифікація»); відповідь має заголовок `Retry-After` (ціле число секунд) |
| 503 | Для `/health/ready`: модель не завантажена або задана в `DATABASE_URL` база не відповіла за 2 с (тіло — `{"status": "not_ready", ...}`, а не `detail`). Для `/predict`: сервер зайнятий — уже виконується `MAX_CONCURRENT_INFERENCES` прогнозів і ще `MAX_QUEUE` запитів чекають; відповідь має заголовок `Retry-After` (секунди до повторної спроби). Для `/predictions`, `/stats` і `/auth/*`: облікові записи й історію вимкнено (не задано `DATABASE_URL`) або до бази даних не вдається підключитися. Інші помилки бази — це помилки сервера (500), а не недоступність |

Тіло помилки має вигляд `{"detail": "..."}`. Для коду 422 у `detail` лежить стандартний
для FastAPI список помилок валідації; `detail` — рядок, коли значення відхилила сама база,
і для всіх 422 від `/auth/*` (там список помилок FastAPI не повертається, бо він повторює
надіслані значення, зокрема пароль).

Текст `detail` — для людей, і він може змінюватися. Там, де клієнт має по-різному
реагувати на помилки з однаковим статусом, тіло містить ще й необов'язкове поле `code` зі
сталим значенням, наприклад `{"detail": "Неправильний пароль.", "code": "wrong_password"}`:

| `code` | Статус | Коли |
|---|---|---|
| `database_not_configured` | 503 | Не задано `DATABASE_URL`: облікових записів та історії немає взагалі (`/auth/*`, історія, статистика). Повторювати запит марно |
| `login_locked` | 429 | Забагато неправильних паролів для цього імені з цієї адреси (`LOGIN_FAILURES_*`): вхід або `DELETE /auth/me` |
| `rate_limited` | 429 | Забагато запитів з цієї адреси за останню хвилину (`RATE_LIMIT_*`), на будь-якому маршруті |
| `wrong_password` | 403 | `DELETE /auth/me` з неправильним паролем; так його можна відрізнити від 403 перевірки `Origin`, де коду немає |
| `body_too_large` | 413 | Тіло запиту до `/auth/*` більше за 8 КіБ (413 від завеликого знімка коду не має) |

В усіх інших помилках поля `code` немає, тож їхні тіла не змінилися. Поле описано в схемі
`ErrorResponse` в OpenAPI (і в типах `frontend/src/api/schema.d.ts`).

Кожна відповідь, зокрема з помилкою, має заголовки `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer` і `X-Frame-Options: DENY`. Відповіді історії (`/predictions`,
`/predictions/{id}`, `/stats`), `/auth/*` і будь-яка відповідь на запит із cookie сесії
мають ще `Cache-Control: no-store`, щоб результати прогнозів і дані користувача не
лишалися в кеші браузера чи проксі.

Формат файлу визначається за його вмістом, а не за розширенням чи заголовком
`Content-Type`. Фото з камер телефонів у форматі MPO (JPEG, після якого йдуть додаткові кадри:
прев'ю чи стереопара) приймаються як JPEG; аналізується перший кадр, тобто саме фото.

## Передобробка

Знімок проходить ті самі кроки, що й під час навчання та перевірки моделі
(`eval_tf2` у навчальному ноутбуці):

1. Перетворення в RGB. Якщо знімок має прозорість (альфа-канал або прозорий колір палітри),
   його спершу накладено на чорне тло: прихованих пікселів модель не бачить. Знімки без
   прозорості, зокрема всі JPEG, перетворюються так само, як під час навчання.
2. `PadToSquare`: знімок розміщується по центру чорного квадрата.
3. `RandomAutocontrast(p=1.0)`.
4. `Resize((224, 224))`.
5. `ToTensor`.
6. `Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])`.

Порядок кроків міняти не можна: автоконтраст працює вже після додавання чорних полів.
Тест `test_transform_is_identical_to_training_notebook` перевіряє, що результат збігається
з кодом із ноутбука точно, до останнього значення.

## Grad-CAM

Теплова карта будується для передбаченого класу за виходом `layer4`, останнього
згорткового блоку ResNet18. Карта накладається на знімок у палітрі `jet`: червоні ділянки
вплинули на рішення моделі найбільше, сині — найменше. Картинка має розмір завантаженого
знімка; якщо його довша сторона перевищує 1024 пікселі, картинка зменшується до 1024.

Grad-CAM показує, на що зважала модель, а не межі пухлини. Карта має роздільність лише
7 × 7 клітинок і розтягується на весь знімок, тому вона груба.

## Примітки щодо залежностей

- **SQLAlchemy 2.0.** Використовується синхронний API SQLAlchemy 2.0 із драйвером psycopg 3.
  Код написано в стилі 2.0, тож перехід на 2.1 не потребуватиме змін.
- **TypeScript 6.0, а не 7.** Шаблон Vite ставить TypeScript 7, але `typescript-eslint`
  поки підтримує версії лише до 6.0. Коли з'явиться підтримка 7, версію можна підняти.
- **`overrides` для `openapi-typescript`.** Пакет оголошує сумісність лише з TypeScript 5.
  Його API для генерації типів у TypeScript 6 не змінилося, тому в `package.json` через
  `overrides` йому дозволено використовувати TypeScript проєкту, і `npm ci` працює без
  `--legacy-peer-deps`.
- **pip і setuptools в образі.** Базовий образ `python:3.12-slim` містить pip 25.0.1 із
  вразливістю CVE-2025-8869, тому `backend/Dockerfile` першим кроком оновлює його до 26.3.
  setuptools у базовому образі немає, але PyTorch оголошує його залежністю, тож він однаково
  потрапляє в образ. Щоб це була версія без CVE-2024-6345 і CVE-2025-47273, setuptools 84.2.1
  встановлюється заздалегідь, ще до PyTorch. Версії залежностей застосунку з
  `requirements.txt` не змінювалися.
- **Кінці рядків.** `.gitattributes` вимагає LF у робочій копії на всіх системах, бо
  Prettier перевіряє саме LF.

## Обмеження

- **Якість моделі.** Модель оцінена 5-кратною перехресною перевіркою на 7013 знімках
  (out-of-fold), точність ≈ 98,1 %.
- **Розмір знімка.** Гліоми у форматі 512×512: recall ≈ 0,99. Гліоми інших розмірів:
  recall ≈ 0,51 (33 з 65). Це зсув домену: знімки різних розмірів відрізняються кадруванням
  і типом послідовності. Для таких знімків сервіс додає попередження
  `unexpected_image_size`. Розмір тут є лише ознакою джерела знімка: якщо просто змінити
  розмір файлу до 512 × 512, попередження зникне, але надійність не зросте.
- **Розмір і джерело знімка.** Розмір знімка корелює з джерелом і класом у датасеті (≈ 99 %
  знімків без пухлини мають розмір не 512×512, ≈ 96 % гліом мають 512×512). Модель могла
  частково використати кадрування як ознаку; це гіпотеза, яку ми перевіряємо окремо, а не
  доведений факт. Класифікатор на основі дерева рішень, який бачить лише ширину й висоту
  файлу, досягає точності ≈ 0,49 (5-кратна перехресна перевірка; частка найчастішого класу
  ≈ 0,25). Модель значно перевершує цей рівень (≈ 0,98), але розмір корелює з джерелом
  знімка, тож повністю виключити його вплив на помилки в групі гліом не 512×512 неможливо.
- **Впевненість.** Модель часто впевнена в помилкових відповідях на таких знімках (середня
  впевненість ≈ 0,86 при точності ≈ 0,51), тому поріг 0,9 ловить лише ≈ 50 % помилок і
  позначає ≈ 3 % знімків. Попередження допомагає, але не гарантує. Поріг задає
  `LOW_CONFIDENCE_THRESHOLD`, а попередження має код `low_confidence`.
- **Оцінка на даних Kaggle.** Модель v2c навчена на об'єднаних Training і Testing з Kaggle,
  тому ці знімки для неї не нові і якість на них оцінювати не можна: чесна оцінка — лише
  цифри перехресної перевірки вище.
- **Пацієнти.** Набір даних не має ідентифікаторів пацієнтів, тому зрізи одного пацієнта
  могли потрапити і в навчання, і в перевірку: справжня точність може бути нижчою.
- **Дані.** Сервіс приймає окремі двовимірні зрізи у форматі JPEG або PNG. DICOM і
  тривимірні дослідження не підтримуються.
- **Розміри знімка.** Знімок може мати не більше 4096 пікселів по довшій стороні
  (`MAX_IMAGE_SIDE`) і не більше 4096 × 4096 пікселів загалом (`MAX_PIXELS`), а файл — не
  більше 10 МБ (`MAX_UPLOAD_MB`). Більші знімки відхиляються з кодом 413 ще до декодування.
- **Глибина кольору й кадри.** 16-бітні зображення не підтримуються: 16-бітні PNG у
  відтінках сірого (їх дають деякі програми перегляду DICOM) відхиляються з кодом 415,
  тож знімок треба експортувати як 8-бітний PNG або JPEG. Сам сервіс у 8 біт їх не
  перетворює, бо не знає, яке вікно яскравості обрати. Виняток — 16-бітні кольорові PNG:
  бібліотека Pillow ще під час читання зводить їх до 8 біт за старшим байтом, тому вони
  приймаються. Анімовані PNG із кількома кадрами відхиляються з кодом 415.
- **Чотири класи.** Модель завжди обирає один із чотирьох класів, навіть якщо на
  зображенні не МРТ мозку або є патологія іншого типу.
- **Не МРТ.** Попередження not_mri_like ловить лише грубі випадки (шум, однорідні й
  кольорові кадри, знімки екрана). Порогові значення підібрані на 7200 знімках датасету
  Kaggle (0 хибних спрацювань) і 16 синтетичних і побутових зразках. Це не детектор вхідних
  даних поза розподілом: сірі зображення, що не є МРТ мозку (рентген, КТ, сіре фото), воно
  не відрізнить, і високу впевненість моделі на таких вхідних даних воно не гарантує
  зупинити.
- **Збільшений шум.** Шумність рахується в роздільності самого файлу, тому шум, збільшений
  із малого зображення, `not_mri_like` не ловить. Наприклад, шум 64 × 64, збільшений у 2
  рази, дає шумність ≈ 0,54, у 4 рази ≈ 0,31, у 8 разів ≈ 0,16: усе нижче порогу 0,85, і
  жодна інша умова не спрацьовує.
- **Кольорові анотації.** Колір рахується як середнє по всьому кадру, тому справжній знімок
  із кольоровою анотацією (плашка, мітка, кольорова шкала) може отримати `not_mri_like`.
  Поріг 7 перевищує навіть червона плашка на ≈ 3 % кадру (колір ≈ 7,8).
- **Безпека.** Історію бачить і видаляє лише її власник (вхід за іменем і паролем, сесія в
  cookie), але немає HTTPS, пошти, скидання пароля і двофакторної автентифікації (див.
  «Автентифікація»). Реєстрація відповідає 409 на зайняте ім'я, тож перевірити, чи існує
  ім'я, можна; від перебору це обмежує лише ліміт входу й реєстрації (10 запитів за
  хвилину з адреси). Частоту запитів і невдалі входи API обмежує за адресою клієнта, в пам'яті одного
  процесу (див. «Rate limiting»). Тому порти в Docker Compose відкрито лише на
  `127.0.0.1`, і сервіс не варто відкривати в публічну мережу. API відповідає лише на
  хости з `ALLOWED_HOSTS` (захист від DNS rebinding) і відхиляє `POST`/`DELETE` зі сторінок
  інших сайтів (`ALLOWED_ORIGINS`), але від програм, що не є браузером (curl, скрипти),
  ці перевірки не захищають: вони не надсилають `Origin`. Діяти від імені користувача така
  програма однаково може лише з його токеном сесії. Документацію API (`/docs`,
  `/redoc`, `/openapi.json`) можна вимкнути через `ENABLE_DOCS=false`.
- **Ресурси контейнерів.** У Docker Compose `api` обмежено 1500 МіБ пам'яті, двома
  процесорами й 200 процесами, `db` — 512 МіБ і 256 процесами, а `frontend` — 128 МіБ і
  64 процесами з файловою системою лише для читання (див. «Запуск через Docker Compose»).
  Ліміти розраховано на типові `MAX_CONCURRENT_INFERENCES` і `MAX_IMAGE_SIDE`.
- **Розгортання.** Compose розрахований на запуск на одному комп'ютері: nginx віддає
  інтерфейс по HTTP лише на `127.0.0.1:8080`. Для доступу з інших машин потрібні HTTPS
  (разом із `SESSION_COOKIE_SECURE=true`) і власна адреса в `ALLOWED_HOSTS` та
  `ALLOWED_ORIGINS`; цього в проєкті немає.
- **Призначення.** Це навчальний проєкт, а не медичний виріб.
