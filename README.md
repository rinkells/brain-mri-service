# Сервіс класифікації МРТ мозку

> **Увага: це навчальний проєкт, а не медичний виріб.**
> Сервіс створено в межах дипломної роботи. Він не проходив клінічних випробувань і
> сертифікації, тому його результати не можна використовувати для діагностики, вибору
> лікування чи будь-яких інших медичних рішень.

Сервіс приймає знімок МРТ мозку (JPEG або PNG) і визначає один із чотирьох класів:
гліома (`glioma`), менінгіома (`meningioma`), пухлина гіпофіза (`pituitary`) або відсутність
пухлини (`notumor`). Разом із класом він повертає ймовірності всіх класів, попередження про
надійність результату і, за бажанням, теплову карту Grad-CAM. Результати прогнозів
зберігаються в історії (PostgreSQL), яку можна переглядати у вебінтерфейсі.

> **Знімки не зберігаються.** В історію потрапляє лише результат прогнозу: клас,
> ймовірності, розмір знімка, попередження, час обробки і версія моделі. Самого зображення,
> назви файлу чи його хешу сервіс не зберігає ні в базі, ні в журналах, бо це медичні дані.
> Під час обробки запиту файл до 1 МБ тримається в пам'яті, а більший FastAPI (Starlette)
> тимчасово записує в системну тимчасову теку (у Docker — `/tmp` контейнера). Після запиту
> цей тимчасовий файл видаляється.

Проєкт складається з трьох частин:

- **бекенд** (`backend/`) — FastAPI-сервіс із моделлю ResNet18 із torchvision, останній шар
  якої замінено на шар із чотирма виходами. Ваги `resnet18_v2c_best.pt` (версія
  `resnet18_v2c`) навчено окремо; у репозиторії їх немає;
- **база даних** — PostgreSQL 16 для історії прогнозів; схема ведеться міграціями Alembic;
- **вебінтерфейс** (`frontend/`) — React + TypeScript на Vite, стилі на Tailwind CSS.

## Запуск через Docker Compose

Найпростіший спосіб запустити бекенд разом із базою. Потрібен Docker Desktop (або Docker
Engine з Compose v2).

1. Покладіть файл ваг у `backend/models/resnet18_v2c_best.pt`.
2. Скопіюйте шаблон змінних і задайте пароль бази:

   ```powershell
   Copy-Item .env.example .env
   ```

   У `.env` замініть `POSTGRES_PASSWORD=change-me` на власний пароль. Пароль стає
   частиною адреси бази, тому використовуйте лише латинські літери, цифри, `-` і `_`.
   Файл `.env` у git не потрапляє; у репозиторії лежить лише `.env.example`.
3. Зберіть і запустіть:

   ```powershell
   docker compose up --build
   ```

Compose запускає два сервіси:

- **`db`** — `postgres:16`; дані зберігаються в томі `pgdata` і переживають перезапуск;
  готовність перевіряється `pg_isready`;
- **`api`** — образ із `backend/`; стартує лише після того, як `db` стане здоровим, спершу
  виконує `alembic upgrade head`, а потім запускає `uvicorn`. Тека `backend/models`
  монтується лише для читання.

Після запуску:

- API: <http://127.0.0.1:8000>, документація: <http://127.0.0.1:8000/docs>;
- Postgres доступний з цього комп'ютера на `127.0.0.1:5433` (порт змінюється в `.env`).

Обидва порти відкрито лише на `127.0.0.1`, бо автентифікації поки немає.

Контейнерам задано ліміти, щоб один збійний запит чи сервіс не забрав усю машину:

| Сервіс | Ліміти | Навіщо |
|---|---|---|
| `api` | `mem_limit: 1500m`, `cpus: 2`, `pids_limit: 200`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]` | Пам'ять і процесор для моделі та `MAX_CONCURRENT_INFERENCES` одночасних прогнозів. Сервер працює від непривілейованого користувача на порту 8000, тому Linux-можливості (capabilities) йому не потрібні, і нових він отримати не може |
| `db` | `mem_limit: 512m`, `pids_limit: 256` | Postgres запускає окремий процес на кожне з'єднання: 256 вистачає на 100 з'єднань (типове `max_connections`) і фонові процеси. Можливості не обмежено: точці входу образу потрібно змінити власника теки з даними й перейти на користувача `postgres` |

Пам'ять `api` виміряно поза Docker (Windows, справжні ваги): ≈ 400 МіБ після старту,
до ≈ 1040 МіБ на мить під час завантаження torch і до ≈ 780 МіБ під час двох одночасних
прогнозів знімка 4096 × 4096 із Grad-CAM. Якщо збільшуєте `MAX_CONCURRENT_INFERENCES`,
збільште й `mem_limit`: коли контейнер виходить за ліміт, ядро завершує процес, і Compose
перезапускає `api` (`restart: unless-stopped`).

Корисні команди:

```powershell
docker compose logs -f api   # журнал бекенду
docker compose down          # зупинити; дані в томі pgdata лишаються
docker compose down -v       # зупинити і видалити всю історію
```

Вебінтерфейс у Compose поки не входить: запустіть його через `npm run dev` (див. нижче),
і він працюватиме з бекендом у Docker.

## Вимоги для розробки без Docker

- Python 3.12;
- Node.js 22 (від 22.13) або 24;
- файл ваг `resnet18_v2c_best.pt`;
- для історії — PostgreSQL (найпростіше `docker compose up -d db`).

**Windows.** PyTorch потребує Microsoft Visual C++ Redistributable. Якщо `import torch`
завершується помилкою `WinError 126`, встановіть
[останню версію цього пакета](https://learn.microsoft.com/cpp/windows/latest-supported-vc-redist).

## Встановлення

Команди для Windows PowerShell, з кореня репозиторію. Віртуальне середовище Python
створюється в корені, а залежності беруться з `backend/`:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend/requirements-dev.txt

cd frontend
npm ci
cd ..
```

У Linux і macOS середовище активується командою `source .venv/bin/activate`.
`requirements-dev.txt` містить залежності сервісу і тестів; для запуску самого сервісу
достатньо `requirements.txt`.

Покладіть файл ваг у `backend/models/resnet18_v2c_best.pt` або вкажіть інший шлях у змінній
`MODEL_PATH`. Без ваг бекенд не запуститься і пояснить причину.

## Запуск у розробці

**Термінал 1 — бекенд** на <http://127.0.0.1:8000>:

```powershell
.\.venv\Scripts\Activate.ps1
cd backend
uvicorn app.main:app --reload --port 8000
```

Без `DATABASE_URL` бекенд працює, але історію не веде: прогнози повертаються з `"id": null`,
а `/predictions` і `/stats` відповідають 503. Щоб увімкнути історію, підніміть лише базу з
Compose і вкажіть її адресу в `backend/.env`:

```powershell
docker compose up -d db
# у backend/.env (пароль — той самий, що в кореневому .env):
# DATABASE_URL=postgresql+psycopg://brain_mri:<пароль>@127.0.0.1:5433/brain_mri
cd backend
alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

Інтерактивна документація API: <http://127.0.0.1:8000/docs>.

**Термінал 2 — вебінтерфейс** на <http://localhost:5173>:

```powershell
cd frontend
npm run dev
```

Відкрийте <http://localhost:5173>. Браузер звертається лише до сервера Vite, а той
пересилає запити `/health`, `/predict`, `/predictions` і `/stats` на бекенд (див.
`server.proxy` у `frontend/vite.config.ts`). Тому налаштовувати CORS на бекенді не потрібно.
Проксі передає бекенду заголовки браузера `Host` і `Origin` (`localhost:5173`), тож вони
мають бути в `ALLOWED_HOSTS` і `ALLOWED_ORIGINS`; типові значення це враховують. Якщо порт
5173 зайнятий, Vite не перейде на інший (`strictPort`), а зупиниться з помилкою: з іншого
порту аналіз і видалення відповідали б 403.
Якщо додаєте в API новий шлях, додайте його і в цей список.

Якщо бекенд не запущено, індикатор у шапці показує «Сервіс недоступний», а спроба аналізу
закінчується повідомленням «Сервер недоступний».

## Можливості інтерфейсу

Сторінка **«Аналіз»**:

- вибір знімка кнопкою або перетягуванням, прев'ю вибраного файлу;
- перевірка формату (JPEG, PNG) і розміру файлу ще до відправки;
- перемикач «Показати теплову карту» і кнопка «Проаналізувати» зі станом завантаження;
- передбачений клас, смужки ймовірностей для чотирьох класів, знімок і теплова карта поруч;
- якщо зображення не схоже на знімок МРТ (`not_mri_like`), над результатом з'являється
  жовтий блок із текстом попередження; якщо модель недостатньо впевнена (`low_confidence`),
  під ним з'являється ще один жовтий блок; розмір знімка не 512 × 512
  (`unexpected_image_size`) позначається дрібною сірою приміткою під результатом; інші
  попередження сервера показуються в жовтому блоці;
- позначка, чи збережено результат в історії;
- зрозумілі повідомлення про помилки 400, 413, 415, 422, про зайнятий сервер (503) і про
  недоступний сервер.

Сторінка **«Історія»**:

- статистика: кількість прогнозів, частка з будь-яким попередженням і окремо частки
  «Не схоже на МРТ», «Низька впевненість» і «Нетиповий розмір знімка», середній час
  обробки, розподіл за класами;
- таблиця прогнозів (час, клас і версія моделі, впевненість, розмір знімка, попередження)
  по 10 на сторінку, від найновішого. Жовті позначки — «Не схоже на МРТ» і «Низька
  впевненість»; нетиповий розмір знімка позначено дрібним сірим текстом, повне
  повідомлення — у підказці;
- фільтр за класом;
- видалення запису з підтвердженням;
- повідомлення, якщо історію вимкнено або база недоступна.

Загальне: індикатор стану сервісу (перевіряє `/health` кожні 15 секунд), світла й темна
теми (вибір запам'ятовується, а за замовчуванням береться з налаштувань системи).
Сторінки перемикаються через адресу (`#/history`), тож працюють оновлення сторінки й кнопка
«Назад». Вибраний знімок і результат аналізу не губляться, поки відкрита історія.

## Налаштування

### Бекенд

Бекенд читає змінні середовища; їх також можна записати у файл `backend/.env` (шаблон —
`backend/.env.example`). Відносні шляхи рахуються від теки, з якої запущено `uvicorn`,
тобто від `backend/`.

| Змінна | Типове значення | Що означає |
|---|---|---|
| `MODEL_PATH` | `models/resnet18_v2c_best.pt` | Шлях до файлу ваг |
| `MODEL_VERSION` | `resnet18_v2c` | Назва ваг із `MODEL_PATH`; повертається в `/health` і `/predict` і зберігається в історії. Змінюйте разом із `MODEL_PATH` |
| `DEVICE` | `cpu` | Пристрій для обчислень: `cpu` або `cuda` |
| `MAX_UPLOAD_MB` | `10` | Найбільший розмір файлу, МБ |
| `MAX_PIXELS` | `16777216` | Найбільша кількість пікселів у знімку (ширина × висота); типове значення відповідає 4096 × 4096 |
| `MAX_IMAGE_SIDE` | `4096` | Найбільша довша сторона знімка, пікселів. Знімок доповнюється до квадрата зі стороною, що дорівнює довшій стороні, тому без цієї межі вузький знімок (наприклад, 16384 × 1024) у межах `MAX_PIXELS` потребував би сотні мегабайтів пам'яті |
| `MAX_CONCURRENT_INFERENCES` | `2` | Скільки прогнозів може виконуватися одночасно |
| `MAX_QUEUE` | `20` | Скільки запитів `/predict` може чекати на вільне місце, поки виконуються `MAX_CONCURRENT_INFERENCES` прогнозів. Наступні отримують 503 із заголовком `Retry-After` |
| `LOW_CONFIDENCE_THRESHOLD` | `0.9` | Поріг від 0 до 1: якщо ймовірність передбаченого класу нижча, прогноз отримує попередження `low_confidence`. Порівнюється неокруглене значення |
| `NOT_MRI_COLOR_MAX` | `7` | Попередження `not_mri_like`, якщо кольоровість (від 0 до 255) більша |
| `NOT_MRI_NOISE_MAX` | `0.85` | Попередження `not_mri_like`, якщо шумність більша |
| `NOT_MRI_STD_MIN` | `10` | Попередження `not_mri_like`, якщо стандартне відхилення яскравості менше: майже однорідний кадр. Від 0 до 127,5: більшого відхилення в яскравості від 0 до 255 не буває, тож більший поріг позначав би кожен знімок |
| `NOT_MRI_LOWCONTRAST_STD` | `30` | Разом із `NOT_MRI_DARK_MIN`: попередження `not_mri_like`, якщо стандартне відхилення яскравості менше за це значення **і** частка темних пікселів менша за `NOT_MRI_DARK_MIN`. Від 0 до 127,5 |
| `NOT_MRI_DARK_MIN` | `0.15` | Частка темних пікселів від 0 до 1 (див. `NOT_MRI_LOWCONTRAST_STD`) |
| `NOT_MRI_OPAQUE_MIN` | `0.99` | Попередження `not_mri_like`, якщо частка повністю непрозорих пікселів (від 0 до 1) менша |
| `DATABASE_URL` | не задано | Адреса бази історії у форматі SQLAlchemy, наприклад `postgresql+psycopg://user:password@host:5432/db`. Без неї історію вимкнено |
| `ENABLE_DOCS` | `true` | Чи віддавати Swagger UI (`/docs`), ReDoc (`/redoc`) і схему `/openapi.json`. `false` прибирає всі три (404) |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1,api` | Значення заголовка `Host` (без порту), на які відповідає API, через кому. На інші — 400. `*` дозволяє будь-який хост. `api` — назва сервісу в Docker Compose |
| `ALLOWED_ORIGINS` | `http://localhost:5173`, `http://127.0.0.1:5173`, `http://localhost:4173`, `http://127.0.0.1:4173`, `http://localhost:8000`, `http://127.0.0.1:8000` | Сторінки (`схема://хост[:порт]`, через кому), з яких браузер може надсилати `POST` і `DELETE`: Vite (`npm run dev`, 5173), `npm run preview` (4173) і Swagger UI самого API (8000). Запит із іншим заголовком `Origin` отримує 403; запити без `Origin` (curl, скрипти) не перевіряються. Порожнє значення забороняє запис із будь-якої сторінки |

Для `DEVICE=cuda` потрібна збірка PyTorch із підтримкою CUDA; як її встановити, описано на
[pytorch.org](https://pytorch.org/get-started/locally/).

### Docker Compose

Compose читає кореневий файл `.env` (шаблон — `.env.example`):

| Змінна | Типове значення | Що означає |
|---|---|---|
| `POSTGRES_USER` | `brain_mri` | Користувач бази |
| `POSTGRES_PASSWORD` | — (обов'язкова) | Пароль бази; лише літери, цифри, `-`, `_` |
| `POSTGRES_DB` | `brain_mri` | Назва бази |
| `POSTGRES_PORT` | `5433` | Порт Postgres на `127.0.0.1` (5433, щоб не конфліктувати з локальним Postgres на 5432) |
| `API_PORT` | `8000` | Порт API на `127.0.0.1` |
| `DEVICE`, `MAX_UPLOAD_MB`, `MAX_PIXELS`, `MAX_IMAGE_SIDE`, `MAX_CONCURRENT_INFERENCES`, `MAX_QUEUE`, `LOW_CONFIDENCE_THRESHOLD`, `NOT_MRI_COLOR_MAX`, `NOT_MRI_NOISE_MAX`, `NOT_MRI_STD_MIN`, `NOT_MRI_LOWCONTRAST_STD`, `NOT_MRI_DARK_MIN`, `NOT_MRI_OPAQUE_MIN`, `ALLOWED_HOSTS`, `ENABLE_DOCS` | як у бекенді | Передаються бекенду |
| `ALLOWED_ORIGINS` | як у бекенді, але порт API береться з `API_PORT` | Передається бекенду; якщо змінили `API_PORT`, Swagger UI однаково працює |

`DATABASE_URL` для сервісу `api` Compose складає сам із цих змінних. Без `POSTGRES_USER`,
`POSTGRES_PASSWORD` або `POSTGRES_DB` команда `docker compose` зупиниться з поясненням.

|---|---|---|
| `VITE_MAX_UPLOAD_MB` | `10` | Найбільший розмір файлу для перевірки в браузері, МБ |

## Історія прогнозів

### Що зберігається

Після кожного успішного `POST /predict` у таблицю `predictions` додається запис, а його `id`
повертається у відповіді. Невдалі запити (400, 413, 415, 422) не зберігаються.

Знімок, назва файлу та його хеш **не зберігаються** (про тимчасовий файл на час запиту див.
на початку README). До міграції `0004` у базі лежав SHA-256 файлу (`image_sha256`), але його
ніщо не читало, а маючи файл, за хешем можна було б перевірити, чи цей знімок аналізували.
Тому стовпець видалено. Як прибрати старі значення з диска, див. «Міграції».

### Схема таблиці `predictions`

| Стовпець | Тип у Postgres | Зміст |
|---|---|---|
| `id` | `uuid`, первинний ключ | Ідентифікатор запису |
| `created_at` | `timestamp with time zone` | Час прогнозу (UTC) |
| `predicted_class` | `varchar(20)` | Передбачений клас; дозволено лише чотири класи |
| `probabilities` | `jsonb` | Ймовірності чотирьох класів |
| `image_width`, `image_height` | `integer` | Розмір знімка в пікселях (більше 0) |
| `warnings` | `jsonb` | Список попереджень (`code`, `message`). Обмеження `ck_predictions_warnings_is_array` (міграція `0003`) дозволяє зберігати тут лише JSON-масив |
| `gradcam_requested` | `boolean` | Чи запитували теплову карту |
| `latency_ms` | `double precision` | Час обробки запиту без збереження в історію, мс. Включає обчислення ознак `not_mri_like` (≈ +6 мс для 512 × 512, до ≈ +0,3 с для 4096 × 4096); у записах, збережених до появи цього попередження, цього часу немає |
| `model_version` | `varchar(64)` | Версія моделі (`MODEL_VERSION`), що зробила прогноз. Записи, збережені до міграції `0002`, отримали `resnet18_v2`; нові записи мають вказувати версію явно |

Індекси: `created_at`, `predicted_class`.

### Міграції

Схема бази ведеться міграціями Alembic у `backend/migrations/`. Адресу бази Alembic бере з
тієї самої змінної `DATABASE_URL`, що й сервіс. Команди виконуються з теки `backend/`:

```powershell
alembic upgrade head                                   # оновити базу до останньої версії
alembic current                                        # поточна версія бази
alembic check                                          # чи збігаються моделі й міграції
alembic revision --autogenerate -m "опис змін"         # нова міграція після зміни records.py
alembic downgrade -1                                   # відкотити останню міграцію
```

Створену автоматично міграцію варто переглянути перед комітом. У Docker Compose
`alembic upgrade head` виконується автоматично перед кожним стартом `api`.

Міграція `0003` додає на Postgres обмеження `CHECK (jsonb_typeof(warnings) = 'array')`.
Спершу вона перевіряє наявні записи: якщо в якомусь `warnings` не масив, міграція
зупиняється, нічого не змінивши, і виводить `id` таких записів (до 20) та їхні значення.
Виправте або видаліть ці записи вручну й запустіть міграцію знову. На SQLite, де немає
`jsonb_typeof`, обмеження не додається.

Міграція `0004` видаляє стовпець `image_sha256` і його індекс зі схеми. Але на PostgreSQL
`DROP COLUMN` лише позначає стовпець видаленим: старі значення лишаються у файлах таблиці,
доки її не буде переписано. Тому після міграції рекомендовано один раз виконати
`VACUUM FULL predictions`, наприклад у Docker Compose (користувач і база — значення
`POSTGRES_USER` і `POSTGRES_DB` з `.env`):

```powershell
docker compose exec db psql -U brain_mri -d brain_mri -c "VACUUM FULL predictions;"
```

Команда переписує таблицю вже без значень видаленого стовпця; на час виконання таблиця
заблокована (для невеликої історії це частки секунди). Резервні копії бази, зроблені до
міграції, хеші містять. `alembic downgrade 0003` повертає стовпець і індекс, але вже як
необов'язковий (`NULL`): старі значення він не відновлює. Хеші в цьому проєкті стосувалися
лише знімків із датасету та тестових файлів: реальних пацієнтів у проєкті немає.

Якщо запис усе ж має пошкоджені попередження (не список, елементи без текстових `code` і
`message`), історія однаково відкривається: такі попередження пропускаються, у журнал
іде повідомлення з `id` запису, а решта полів повертається як звичайно. `/stats` рахує
лише коректні попередження.

### Якщо база недоступна

Прогноз однаково повертається, але з `"id": null`, а помилка записується в журнал. Щоб
кожен прогноз не чекав на недоступну базу кілька секунд, після помилки сервіс 30 секунд не
звертається до неї для збереження: такі прогнози теж не зберігаються, а в журнал іде
попередження. Ендпоінти історії тим часом відповідають 503, а `/health` — 200. Коли база
повертається, збереження відновлюється само.

## Тести та перевірки

**Бекенд** (з активованим середовищем):

```powershell
cd backend
pytest
```

Тести не потребують ні справжніх ваг, ні Postgres. Модель у них — ResNet18 із випадковими
вагами (один вихід посилено, щоб модель була впевненою і попередження `low_confidence`
з'являлося лише в тестах, які його перевіряють), а історія зберігається в SQLite у пам'яті. Тести покривають збереження прогнозів,
пагінацію, фільтр, видалення, `/stats`, роботу без `DATABASE_URL` і з недоступною базою,
поріг попередження `low_confidence`, ознаки й пороги попередження `not_mri_like` (на
синтетичних зображеннях: шум, суцільні й кольорові кадри, схожий на знімок сірий кадр),
а також міграції: їхню відповідність моделям і
заповнення `model_version` для старих записів, видалення й відновлення `image_sha256` (міграція
`0004` вгору й униз на SQLite). Один тест додатково перевіряє справжні ваги,
якщо файл `backend/models/resnet18_v2c_best.pt` є на місці, а інакше пропускається.

**Вебінтерфейс:**

```powershell
cd frontend
npm test              # Vitest + React Testing Library, один прогін
npm run test:watch    # перезапуск тестів після змін
npm run typecheck     # перевірка типів TypeScript
npm run lint          # ESLint
npm run format:check  # Prettier; npm run format виправляє форматування
```

Тести вебінтерфейсу не звертаються до бекенду: `fetch` у них замокано. Вони перевіряють

## API

### `GET /health`

Повертає стан сервісу, пристрій, класи в порядку виходів моделі і версію моделі. Від бази
не залежить і відповідає одразу, навіть коли сервер зайнятий прогнозами: запити до
`/predict` чекають своєї черги, не займаючи потоків, якими користуються інші ендпоінти.

```json
{
  "status": "ok",
  "device": "cpu",
  "classes": ["glioma", "meningioma", "notumor", "pituitary"],
  "model_version": "resnet18_v2c"
}
```

### `POST /predict`

Знімок передається у полі `file` запиту `multipart/form-data`. Параметр `gradcam=true`
додає до відповіді теплову карту.

Одночасно виконується не більше `MAX_CONCURRENT_INFERENCES` прогнозів (типово 2). Інші
запити чекають у черзі довжиною до `MAX_QUEUE` (типово 20), а якщо й вона заповнена,
сервер одразу відповідає 503 із заголовком `Retry-After: 5`.

```powershell
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict"
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true"
```

Приклад відповіді для знімка 640 × 480 без теплової карти:

```json
{
  "id": "43eb20d2-5203-42e7-8903-a86a82a76fbf",
  "predicted_class": "meningioma",
  "probabilities": {
    "glioma": 0.0012,
    "meningioma": 0.9988,
    "notumor": 0.00004,
    "pituitary": 0.0000001
  },
  "image_size": {"width": 640, "height": 480},
  "warnings": [
    {
      "code": "unexpected_image_size",
      "message": "Розмір знімка відрізняється від 512×512. Для гліом такого формату recall у перевірці був ≈ 0,51 (проти ≈ 0,99 для 512×512): якщо є підозра на гліому, результат менш надійний."
    }
  ],
  "gradcam_png_base64": null,
  "model_version": "resnet18_v2c"
}
```

| Поле | Зміст |
|---|---|
| `id` | Ідентифікатор запису в історії; `null`, якщо історію вимкнено або запис не вдалося зберегти |
| `predicted_class` | Клас із найбільшою ймовірністю |
| `probabilities` | Ймовірності чотирьох класів; у сумі дають 1 |
| `image_size` | Розмір завантаженого знімка в пікселях |
| `warnings` | Список попереджень (`code`, `message`); порожній список, якщо попереджень немає. Коди: `not_mri_like` — зображення не схоже на знімок МРТ (див. нижче), завжди йде першим; `unexpected_image_size` — розмір знімка не 512 × 512; `low_confidence` — ймовірність передбаченого класу нижча за `LOW_CONFIDENCE_THRESHOLD` |
| `gradcam_png_base64` | Теплова карта у форматі PNG, закодована в base64; `null`, якщо її не просили |
| `model_version` | Версія моделі, що зробила прогноз (`MODEL_VERSION`) |

**Попередження `not_mri_like`.** Модель упевнено класифікує будь-яке зображення, зокрема
шум чи фото. Тому сервіс рахує на декодованому знімку в його власній роздільності чотири
прості ознаки, а також частку непрозорих пікселів файлу, і додає попередження, якщо
виконується хоча б одна умова (усі порівняння строгі: значення, що дорівнює порогу,
попередження не дає):

- кольоровість (середнє по пікселях `max(|R−G|, |G−B|, |R−B|)`) більша за `NOT_MRI_COLOR_MAX` (7);
- шумність (середній модуль різниці сусідніх пікселів, поділений на стандартне відхилення
  яскравості) більша за `NOT_MRI_NOISE_MAX` (0,85);
- стандартне відхилення яскравості менше за `NOT_MRI_STD_MIN` (10): майже однорідний кадр.
  Для суцільного кадру (відхилення 0) шумність не визначена, і спрацьовує саме ця умова;
- стандартне відхилення менше за `NOT_MRI_LOWCONTRAST_STD` (30) **і** частка темних пікселів
  (яскравість нижче 10 % шкали) менша за `NOT_MRI_DARK_MIN` (0,15): тьмяне зображення без
  темного фону, який має кожен знімок;
- частка повністю непрозорих пікселів менша за `NOT_MRI_OPAQUE_MIN` (0,99). Сервіс малює
  прозорі пікселі чорними, і без цієї умови прозорі поля ставали б фальшивим темним фоном:
  тьмяний шум зі смугами прозорості по 60 пікселів з боків проходив би решту перевірок. У
  датасеті прозорості немає: альфа-канал мають лише 3 файли з 7200, і в них непрозорі всі
  пікселі.

Це попередження, а не відмова: прогноз повертається як завжди. На 7200 знімках датасету
Kaggle найбільша кольоровість 5,66, найбільша шумність 0,62, найменше відхилення 20,8, а
умову низького контрасту не виконує жоден знімок. Тобто жоден знімок попередження не
отримує, а всі 16 перевірених зразків отримують: шум, суцільні кадри, 8 кольорових фото,
знімок екрана. Межі методу див. в «Обмеженнях».

Ознаки рахуються смугами по 512 рядків через гістограми Pillow. Суми цілі, тож результат
точний, а повної копії зображення не створюється. На машині розробника (Windows, CPU) це
займає ≈ 6 мс для 512 × 512 (сам прогноз моделі ≈ 40 мс) і ≈ 0,3 с та ≈ 30 МіБ пам'яті
для найбільшого допустимого 4096 × 4096 (прогноз моделі ≈ 0,2 с). У сірих файлах (режими
`L`, `LA`, `1`; таких 3067 із 7200 знімків датасету) кольору немає, тож він не рахується:
сірий 4096 × 4096 займає ≈ 0,12 с.

Приклад відповіді для зображення 512 × 512 із випадковим шумом: модель майже впевнена, що
пухлини немає, і лише попередження каже, що це не знімок:

```json
{
  "id": "0d6a3f8e-7c41-4b1e-9a52-3e8f2b9c1d70",
  "predicted_class": "notumor",
  "probabilities": {
    "glioma": 0.0028,
    "meningioma": 0.0012,
    "notumor": 0.9928,
    "pituitary": 0.0033
  },
  "image_size": {"width": 512, "height": 512},
  "warnings": [
    {
      "code": "not_mri_like",
      "message": "Зображення не схоже на знімок МРТ (кольорове, шумне, однорідне або без темного фону). Результат не можна вважати достовірним."
    }
  ],
  "gradcam_png_base64": null,
  "model_version": "resnet18_v2c"
}
```

Зберегти теплову карту у файл можна так:

```powershell
$r = curl.exe -s -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true" | ConvertFrom-Json
[IO.File]::WriteAllBytes("$PWD\gradcam.png", [Convert]::FromBase64String($r.gradcam_png_base64))
```

### `GET /predictions`

Сторінка історії, від найновішого запису.

| `predicted_class` | — | Лише прогнози цього класу |

```powershell
curl.exe "http://127.0.0.1:8000/predictions?limit=10&offset=0&predicted_class=glioma"
```

```json
{
  "items": [
    {
      "id": "43eb20d2-5203-42e7-8903-a86a82a76fbf",

      "probabilities": {"glioma": 0.91, "meningioma": 0.05, "notumor": 0.03, "pituitary": 0.01},
```

`total` — кількість усіх записів, що відповідають фільтру, а не лише цієї сторінки.

### `GET /predictions/{id}`

Один запис у тому самому форматі, що й елемент `items`. Якщо запису немає — 404.

### `DELETE /predictions/{id}`

Видаляє запис. Успіх — 204 без тіла; якщо запису немає — 404. Якщо той самий запис
видаляють кілька запитів одночасно, 204 отримує лише один із них, решта — 404.

### `GET /stats`

```json
{
  "total": 3,
  "by_class": {"glioma": 0, "meningioma": 2, "notumor": 1, "pituitary": 0},
  "with_warnings_share": 0.3333,
  "average_latency_ms": 118.6,
  "warnings_by_code": {"unexpected_image_size": 1, "low_confidence": 0, "not_mri_like": 0}
}
```

| Поле | Зміст |
|---|---|
| `total` | Кількість збережених прогнозів |
| `by_class` | Кількість прогнозів для кожного класу |
| `with_warnings_share` | Частка прогнозів із будь-яким попередженням (від 0 до 1); прогноз із кількома попередженнями рахується один раз |
| `average_latency_ms` | Середній час обробки, мс. Змішує записи до й після появи `not_mri_like`: новіші включають ще й обчислення його ознак (≈ +6 мс для 512 × 512, до ≈ +0,3 с для 4096 × 4096) |
| `warnings_by_code` | Кількість прогнозів із кожним кодом попередження. Прогноз із кількома попередженнями враховується в кожному з них, тому сума може перевищувати кількість прогнозів із попередженнями. `unexpected_image_size`, `low_confidence` і `not_mri_like` є завжди, навіть із 0; інші коди з'являються, коли трапляються |

Поки прогнозів немає, `with_warnings_share` і `average_latency_ms` дорівнюють `null`, а
`warnings_by_code` містить нулі. Поле `warnings_by_code` додано без зміни наявних полів.

Усі числа описують один момент, навіть якщо тим часом зберігаються нові прогнози:
кількості й середній час рахуються одним SQL-запитом (тому `total` завжди дорівнює сумі
`by_class`), а на Postgres обидва запити `/stats` виконуються в одній транзакції
`REPEATABLE READ`.

### Помилки

| Код | Коли виникає |
|---|---|
| 400 | Файл порожній, не є зображенням або пошкоджений; або заголовок `Host` не входить до `ALLOWED_HOSTS` (тоді тіло відповіді — текст `Invalid host header`) |
| 403 | `POST` або `DELETE` із заголовком `Origin`, якого немає в `ALLOWED_ORIGINS` (запит зі сторінки іншого сайту) |
| 404 | Запису з таким `id` в історії немає |
| 413 | Файл більший за `MAX_UPLOAD_MB`, знімок має більше пікселів, ніж `MAX_PIXELS`, або його довша сторона більша за `MAX_IMAGE_SIDE` |
| 415 | Зображення не у форматі JPEG чи PNG (наприклад, GIF, BMP, TIFF, WEBP), 16-бітне (зокрема 16-бітний PNG у відтінках сірого) або має кілька кадрів (анімований PNG) |
| 422 | Некоректний запит: немає поля `file`, неправильний `gradcam`, `limit`, `offset`, клас або `id`; також якщо значення із запиту не прийняла сама база даних |
| 503 | Для `/predict`: сервер зайнятий — уже виконується `MAX_CONCURRENT_INFERENCES` прогнозів і ще `MAX_QUEUE` запитів чекають; відповідь має заголовок `Retry-After` (секунди до повторної спроби). Для `/predictions` і `/stats`: історію вимкнено (не задано `DATABASE_URL`) або до бази даних не вдається підключитися. Інші помилки бази — це помилки сервера (500), а не недоступність |

Тіло помилки має вигляд `{"detail": "..."}`. Для коду 422 у `detail` лежить стандартний
для FastAPI список помилок валідації; лише коли значення відхилила сама база, `detail` —
рядок.

Кожна відповідь, зокрема з помилкою, має заголовки `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer` і `X-Frame-Options: DENY`. Відповіді історії (`/predictions`,
`/predictions/{id}`, `/stats`) мають ще `Cache-Control: no-store`, щоб результати прогнозів
не лишалися в кеші браузера чи проксі.

Формат файлу визначається за його вмістом, а не за розширенням чи заголовком
`Content-Type`. Фото з камер телефонів у форматі MPO (JPEG, після якого йдуть додаткові кадри:
прев'ю чи стереопара) приймаються як JPEG; аналізується перший кадр, тобто саме фото.

## Передобробка

Знімок проходить ті самі кроки, що й під час навчання та перевірки моделі
(`eval_tf2` у навчальному ноутбуці):

1. Перетворення в RGB. Якщо знімок має прозорість (альфа-канал або прозорий колір палітри),
   його спершу накладено на чорне тло: прихованих пікселів модель не бачить. Знімки без
   прозорості, зокрема всі JPEG, перетворюються так само, як під час навчання.
2. `PadToSquare`: знімок розміщується по центру чорного квадрата.
3. `RandomAutocontrast(p=1.0)`.
4. `Resize((224, 224))`.
5. `ToTensor`.
6. `Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])`.

Порядок кроків міняти не можна: автоконтраст працює вже після додавання чорних полів.
Тест `test_transform_is_identical_to_training_notebook` перевіряє, що результат збігається
з кодом із ноутбука точно, до останнього значення.

## Grad-CAM

Теплова карта будується для передбаченого класу за виходом `layer4`, останнього
згорткового блоку ResNet18. Карта накладається на знімок у палітрі `jet`: червоні ділянки
вплинули на рішення моделі найбільше, сині — найменше. Картинка має розмір завантаженого
знімка; якщо його довша сторона перевищує 1024 пікселі, картинка зменшується до 1024.

Grad-CAM показує, на що зважала модель, а не межі пухлини. Карта має роздільність лише
7 × 7 клітинок і розтягується на весь знімок, тому вона груба.

## Примітки щодо залежностей

- **SQLAlchemy 2.0.** Використовується синхронний API SQLAlchemy 2.0 із драйвером psycopg 3.
  Код написано в стилі 2.0, тож перехід на 2.1 не потребуватиме змін.
- **TypeScript 6.0, а не 7.** Шаблон Vite ставить TypeScript 7, але `typescript-eslint`
  поки підтримує версії лише до 6.0. Коли з'явиться підтримка 7, версію можна підняти.
- **`overrides` для `openapi-typescript`.** Пакет оголошує сумісність лише з TypeScript 5.
  Його API для генерації типів у TypeScript 6 не змінилося, тому в `package.json` через
  `overrides` йому дозволено використовувати TypeScript проєкту, і `npm ci` працює без
  `--legacy-peer-deps`.
- **pip і setuptools в образі.** Базовий образ `python:3.12-slim` містить pip 25.0.1 із
  вразливістю CVE-2025-8869, тому `backend/Dockerfile` першим кроком оновлює його до 26.3.
  setuptools у базовому образі немає, але PyTorch оголошує його залежністю, тож він однаково
  потрапляє в образ. Щоб це була версія без CVE-2024-6345 і CVE-2025-47273, setuptools 84.2.1
  встановлюється заздалегідь, ще до PyTorch. Версії залежностей застосунку з
  `requirements.txt` не змінювалися.
- **Кінці рядків.** `.gitattributes` вимагає LF у робочій копії на всіх системах, бо
  Prettier перевіряє саме LF.

## Обмеження

- **Якість моделі.** Модель оцінена 5-кратною перехресною перевіркою на 7013 знімках
  (out-of-fold), точність ≈ 98,1 %.
- **Розмір знімка.** Гліоми у форматі 512×512: recall ≈ 0,99. Гліоми інших розмірів:
  recall ≈ 0,51 (33 з 65). Це зсув домену: знімки різних розмірів відрізняються кадруванням
  і типом послідовності. Для таких знімків сервіс додає попередження
  `unexpected_image_size`. Розмір тут є лише ознакою джерела знімка: якщо просто змінити
  розмір файлу до 512 × 512, попередження зникне, але надійність не зросте.
- **Розмір і джерело знімка.** Розмір знімка корелює з джерелом і класом у датасеті (≈ 99 %
  знімків без пухлини мають розмір не 512×512, ≈ 96 % гліом мають 512×512). Модель могла
  частково використати кадрування як ознаку; це гіпотеза, яку ми перевіряємо окремо, а не
  доведений факт. Класифікатор на основі дерева рішень, який бачить лише ширину й висоту
  файлу, досягає точності ≈ 0,49 (5-кратна перехресна перевірка; частка найчастішого класу
  ≈ 0,25). Модель значно перевершує цей рівень (≈ 0,98), але розмір корелює з джерелом
  знімка, тож повністю виключити його вплив на помилки в групі гліом не 512×512 неможливо.
- **Впевненість.** Модель часто впевнена в помилкових відповідях на таких знімках (середня
  впевненість ≈ 0,86 при точності ≈ 0,51), тому поріг 0,9 ловить лише ≈ 50 % помилок і
  позначає ≈ 3 % знімків. Попередження допомагає, але не гарантує. Поріг задає
  `LOW_CONFIDENCE_THRESHOLD`, а попередження має код `low_confidence`.
- **Оцінка на даних Kaggle.** Модель v2c навчена на об'єднаних Training і Testing з Kaggle,
  тому ці знімки для неї не нові і якість на них оцінювати не можна: чесна оцінка — лише
  цифри перехресної перевірки вище.
- **Пацієнти.** Набір даних не має ідентифікаторів пацієнтів, тому зрізи одного пацієнта
  могли потрапити і в навчання, і в перевірку: справжня точність може бути нижчою.
- **Дані.** Сервіс приймає окремі двовимірні зрізи у форматі JPEG або PNG. DICOM і
  тривимірні дослідження не підтримуються.
- **Розміри знімка.** Знімок може мати не більше 4096 пікселів по довшій стороні
  (`MAX_IMAGE_SIDE`) і не більше 4096 × 4096 пікселів загалом (`MAX_PIXELS`), а файл — не
  більше 10 МБ (`MAX_UPLOAD_MB`). Більші знімки відхиляються з кодом 413 ще до декодування.
- **Глибина кольору й кадри.** 16-бітні зображення не підтримуються: 16-бітні PNG у
  відтінках сірого (їх дають деякі програми перегляду DICOM) відхиляються з кодом 415,
  тож знімок треба експортувати як 8-бітний PNG або JPEG. Сам сервіс у 8 біт їх не
  перетворює, бо не знає, яке вікно яскравості обрати. Виняток — 16-бітні кольорові PNG:
  бібліотека Pillow ще під час читання зводить їх до 8 біт за старшим байтом, тому вони
  приймаються. Анімовані PNG із кількома кадрами відхиляються з кодом 415.
- **Чотири класи.** Модель завжди обирає один із чотирьох класів, навіть якщо на
  зображенні не МРТ мозку або є патологія іншого типу.
- **Не МРТ.** Попередження not_mri_like ловить лише грубі випадки (шум, однорідні й
  кольорові кадри, знімки екрана). Порогові значення підібрані на 7200 знімках датасету
  Kaggle (0 хибних спрацювань) і 16 синтетичних і побутових зразках. Це не детектор вхідних
  даних поза розподілом: сірі зображення, що не є МРТ мозку (рентген, КТ, сіре фото), воно
  не відрізнить, і високу впевненість моделі на таких вхідних даних воно не гарантує
  зупинити.
- **Збільшений шум.** Шумність рахується в роздільності самого файлу, тому шум, збільшений
  із малого зображення, `not_mri_like` не ловить. Наприклад, шум 64 × 64, збільшений у 2
  рази, дає шумність ≈ 0,54, у 4 рази ≈ 0,31, у 8 разів ≈ 0,16: усе нижче порогу 0,85, і
  жодна інша умова не спрацьовує.
- **Кольорові анотації.** Колір рахується як середнє по всьому кадру, тому справжній знімок
  із кольоровою анотацією (плашка, мітка, кольорова шкала) може отримати `not_mri_like`.
  Поріг 7 перевищує навіть червона плашка на ≈ 3 % кадру (колір ≈ 7,8).
- **Безпека.** Автентифікації й обмеження частоти запитів немає: будь-хто з доступом до
  API бачить і може видаляти історію. Тому порти в Docker Compose відкрито лише на
  `127.0.0.1`, і сервіс не варто відкривати в публічну мережу. API відповідає лише на
  хости з `ALLOWED_HOSTS` (захист від DNS rebinding) і відхиляє `POST`/`DELETE` зі сторінок
  інших сайтів (`ALLOWED_ORIGINS`), але від програм, що не є браузером (curl, скрипти),
  ці перевірки не захищають: вони не надсилають `Origin`. Документацію API (`/docs`,
  `/redoc`, `/openapi.json`) можна вимкнути через `ENABLE_DOCS=false`.
- **Ресурси контейнерів.** У Docker Compose `api` обмежено 1500 МіБ пам'яті, двома
  процесорами й 200 процесами, а `db` — 512 МіБ і 256 процесами (див. «Запуск через Docker
  Compose»). Ліміти розраховано на типові `MAX_CONCURRENT_INFERENCES` і `MAX_IMAGE_SIDE`.
- **Продакшн-збірка вебінтерфейсу** (nginx або віддача `dist` з FastAPI) ще не зроблена.
- **Призначення.** Це навчальний проєкт, а не медичний виріб.
