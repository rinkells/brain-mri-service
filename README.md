# Сервіс класифікації МРТ мозку

> **Увага: це навчальний проєкт, а не медичний виріб.**
> Сервіс створено в межах дипломної роботи. Він не проходив клінічних випробувань і
> сертифікації, тому його результати не можна використовувати для діагностики, вибору
> лікування чи будь-яких інших медичних рішень.

Сервіс приймає знімок МРТ мозку (JPEG або PNG) і визначає один із чотирьох класів:
гліома (`glioma`), менінгіома (`meningioma`), пухлина гіпофіза (`pituitary`) або відсутність
пухлини (`notumor`). Разом із класом він повертає ймовірності всіх класів, попередження про
надійність результату і, за бажанням, теплову карту Grad-CAM. Результати прогнозів
зберігаються в історії (PostgreSQL), яку можна переглядати у вебінтерфейсі.

> **Знімки не зберігаються.** В історію потрапляє лише результат прогнозу: клас,
> ймовірності, розмір знімка, попередження, час обробки і SHA-256 файлу. Самого
> зображення та назви файлу сервіс ніде не записує, бо це медичні дані.

Проєкт складається з трьох частин:

- **бекенд** (`backend/`) — FastAPI-сервіс із моделлю ResNet18 із torchvision, останній шар
  якої замінено на шар із чотирма виходами. Ваги `resnet18_v2_best.pt` навчено окремо; у
  репозиторії їх немає;
- **база даних** — PostgreSQL 16 для історії прогнозів; схема ведеться міграціями Alembic;
- **вебінтерфейс** (`frontend/`) — React + TypeScript на Vite, стилі на Tailwind CSS.

## Запуск через Docker Compose

Найпростіший спосіб запустити бекенд разом із базою. Потрібен Docker Desktop (або Docker
Engine з Compose v2).

1. Покладіть файл ваг у `backend/models/resnet18_v2_best.pt`.
2. Скопіюйте шаблон змінних і задайте пароль бази:

   ```powershell
   Copy-Item .env.example .env
   ```

   У `.env` замініть `POSTGRES_PASSWORD=change-me` на власний пароль. Пароль стає
   частиною адреси бази, тому використовуйте лише латинські літери, цифри, `-` і `_`.
   Файл `.env` у git не потрапляє; у репозиторії лежить лише `.env.example`.
3. Зберіть і запустіть:

   ```powershell
   docker compose up --build
   ```

Compose запускає два сервіси:

- **`db`** — `postgres:16`; дані зберігаються в томі `pgdata` і переживають перезапуск;
  готовність перевіряється `pg_isready`;
- **`api`** — образ із `backend/`; стартує лише після того, як `db` стане здоровим, спершу
  виконує `alembic upgrade head`, а потім запускає `uvicorn`. Тека `backend/models`
  монтується лише для читання.

Після запуску:

- API: <http://127.0.0.1:8000>, документація: <http://127.0.0.1:8000/docs>;
- Postgres доступний з цього комп'ютера на `127.0.0.1:5433` (порт змінюється в `.env`).

Обидва порти відкрито лише на `127.0.0.1`, бо автентифікації поки немає.

Корисні команди:

```powershell
docker compose logs -f api   # журнал бекенду
docker compose down          # зупинити; дані в томі pgdata лишаються
docker compose down -v       # зупинити і видалити всю історію
```

Вебінтерфейс у Compose поки не входить: запустіть його через `npm run dev` (див. нижче),
і він працюватиме з бекендом у Docker.

## Встановлення

Команди для Windows PowerShell, з кореня репозиторію. Віртуальне середовище Python
створюється в корені, а залежності беруться з `backend/`:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend/requirements-dev.txt

cd frontend
npm ci
cd ..
```

У Linux і macOS середовище активується командою `source .venv/bin/activate`.
`requirements-dev.txt` містить залежності сервісу і тестів; для запуску самого сервісу
достатньо `requirements.txt`.

Покладіть файл ваг у `backend/models/resnet18_v2_best.pt` або вкажіть інший шлях у змінній
`MODEL_PATH`. Без ваг бекенд не запуститься і пояснить причину.

## Запуск у розробці

**Термінал 1 — бекенд** на <http://127.0.0.1:8000>:

```powershell
.\.venv\Scripts\Activate.ps1
cd backend
uvicorn app.main:app --reload --port 8000
```

Без `DATABASE_URL` бекенд працює, але історію не веде: прогнози повертаються з `"id": null`,
а `/predictions` і `/stats` відповідають 503. Щоб увімкнути історію, підніміть лише базу з
Compose і вкажіть її адресу в `backend/.env`:

```powershell
docker compose up -d db
# у backend/.env (пароль — той самий, що в кореневому .env):
# DATABASE_URL=postgresql+psycopg://brain_mri:<пароль>@127.0.0.1:5433/brain_mri
cd backend
alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

Інтерактивна документація API: <http://127.0.0.1:8000/docs>.

**Термінал 2 — вебінтерфейс** на <http://localhost:5173>:

```powershell
cd frontend
npm run dev
```

Відкрийте <http://localhost:5173>. Браузер звертається лише до сервера Vite, а той
пересилає запити `/health`, `/predict`, `/predictions` і `/stats` на бекенд (див.
`server.proxy` у `frontend/vite.config.ts`). Тому налаштовувати CORS на бекенді не потрібно.
Якщо додаєте в API новий шлях, додайте його і в цей список.

Якщо бекенд не запущено, індикатор у шапці показує «Сервіс недоступний», а спроба аналізу
закінчується повідомленням «Сервер недоступний».

## Можливості інтерфейсу

Сторінка **«Аналіз»**:

- вибір знімка кнопкою або перетягуванням, прев'ю вибраного файлу;
- перевірка формату (JPEG, PNG) і розміру файлу ще до відправки;
- перемикач «Показати теплову карту» і кнопка «Проаналізувати» зі станом завантаження;
- передбачений клас, смужки ймовірностей для чотирьох класів, знімок і теплова карта поруч;
- попередження від сервера в жовтому блоці;
- позначка, чи збережено результат в історії;
- зрозумілі повідомлення про помилки 400, 413, 415, 422 і про недоступний сервер.

Сторінка **«Історія»**:

- статистика: кількість прогнозів, частка з попередженнями, середній час обробки,
  розподіл за класами;
- таблиця прогнозів (час, клас, впевненість, розмір знімка, чи є попередження) по 10 на
  сторінку, від найновішого;
- фільтр за класом;
- видалення запису з підтвердженням;
- повідомлення, якщо історію вимкнено або база недоступна.

Загальне: індикатор стану сервісу (перевіряє `/health` кожні 15 секунд), світла й темна
теми (вибір запам'ятовується, а за замовчуванням береться з налаштувань системи).
Сторінки перемикаються через адресу (`#/history`), тож працюють оновлення сторінки й кнопка
«Назад». Вибраний знімок і результат аналізу не губляться, поки відкрита історія.

## Налаштування

### Бекенд

Бекенд читає змінні середовища; їх також можна записати у файл `backend/.env` (шаблон —
`backend/.env.example`). Відносні шляхи рахуються від теки, з якої запущено `uvicorn`,
тобто від `backend/`.

| Змінна | Типове значення | Що означає |
|---|---|---|
| `MODEL_PATH` | `models/resnet18_v2_best.pt` | Шлях до файлу ваг |
| `DEVICE` | `cpu` | Пристрій для обчислень: `cpu` або `cuda` |
| `MAX_UPLOAD_MB` | `10` | Найбільший розмір файлу, МБ |
| `MAX_PIXELS` | `16777216` | Найбільша кількість пікселів у знімку (ширина × висота); типове значення відповідає 4096 × 4096 |
| `DATABASE_URL` | не задано | Адреса бази історії у форматі SQLAlchemy, наприклад `postgresql+psycopg://user:password@host:5432/db`. Без неї історію вимкнено |

Для `DEVICE=cuda` потрібна збірка PyTorch із підтримкою CUDA; як її встановити, описано на
[pytorch.org](https://pytorch.org/get-started/locally/).

### Docker Compose

Compose читає кореневий файл `.env` (шаблон — `.env.example`):

| Змінна | Типове значення | Що означає |
|---|---|---|
| `POSTGRES_USER` | `brain_mri` | Користувач бази |
| `POSTGRES_PASSWORD` | — (обов'язкова) | Пароль бази; лише літери, цифри, `-`, `_` |
| `POSTGRES_DB` | `brain_mri` | Назва бази |
| `POSTGRES_PORT` | `5433` | Порт Postgres на `127.0.0.1` (5433, щоб не конфліктувати з локальним Postgres на 5432) |
| `API_PORT` | `8000` | Порт API на `127.0.0.1` |
| `DEVICE`, `MAX_UPLOAD_MB`, `MAX_PIXELS` | як у бекенді | Передаються бекенду |

`DATABASE_URL` для сервісу `api` Compose складає сам із цих змінних. Без `POSTGRES_USER`,
`POSTGRES_PASSWORD` або `POSTGRES_DB` команда `docker compose` зупиниться з поясненням.

### Вебінтерфейс

| Змінна | Типове значення | Що означає |
|---|---|---|
| `VITE_MAX_UPLOAD_MB` | `10` | Найбільший розмір файлу для перевірки в браузері, МБ |

Якщо змінюєте `MAX_UPLOAD_MB` бекенду, задайте те саме значення у файлі
`frontend/.env.local` (у git він не потрапляє), наприклад `VITE_MAX_UPLOAD_MB=20`, і
перезапустіть `npm run dev`. Бекенд однаково перевіряє розмір сам.

## Історія прогнозів

### Що зберігається

Після кожного успішного `POST /predict` у таблицю `predictions` додається запис, а його `id`
повертається у відповіді. Невдалі запити (400, 413, 415, 422) не зберігаються.

Знімок і назва файлу **не зберігаються**. SHA-256 файлу дає змогу помітити повторне
завантаження того самого знімка, але відновити з нього зображення неможливо.

### Схема таблиці `predictions`

| Стовпець | Тип у Postgres | Зміст |
|---|---|---|
| `id` | `uuid`, первинний ключ | Ідентифікатор запису |
| `created_at` | `timestamp with time zone` | Час прогнозу (UTC) |
| `predicted_class` | `varchar(20)` | Передбачений клас; дозволено лише чотири класи |
| `probabilities` | `jsonb` | Ймовірності чотирьох класів |
| `image_width`, `image_height` | `integer` | Розмір знімка в пікселях (більше 0) |
| `warnings` | `jsonb` | Список попереджень (`code`, `message`) |
| `image_sha256` | `varchar(64)` | SHA-256 завантаженого файлу (hex) |
| `gradcam_requested` | `boolean` | Чи запитували теплову карту |
| `latency_ms` | `double precision` | Час обробки запиту без збереження в історію, мс |

Індекси: `created_at`, `predicted_class`, `image_sha256`.

### Міграції

Схема бази ведеться міграціями Alembic у `backend/migrations/`. Адресу бази Alembic бере з
тієї самої змінної `DATABASE_URL`, що й сервіс. Команди виконуються з теки `backend/`:

```powershell
alembic upgrade head                                   # оновити базу до останньої версії
alembic current                                        # поточна версія бази
alembic check                                          # чи збігаються моделі й міграції
alembic revision --autogenerate -m "опис змін"         # нова міграція після зміни records.py
alembic downgrade -1                                   # відкотити останню міграцію
```

Створену автоматично міграцію варто переглянути перед комітом. У Docker Compose
`alembic upgrade head` виконується автоматично перед кожним стартом `api`.

### Якщо база недоступна

Прогноз однаково повертається, але з `"id": null`, а помилка записується в журнал. Щоб
кожен прогноз не чекав на недоступну базу кілька секунд, після помилки сервіс 30 секунд не
звертається до неї для збереження: такі прогнози теж не зберігаються, а в журнал іде
попередження. Ендпоінти історії тим часом відповідають 503, а `/health` — 200. Коли база
повертається, збереження відновлюється само.

## Типи API

Типи TypeScript для запитів і відповідей генеруються з OpenAPI-схеми FastAPI пакетом
`openapi-typescript`. Згенерований файл `frontend/src/api/schema.d.ts` лежить у репозиторії,
тому для звичайної роботи генерувати його не потрібно.

Після зміни API бекенду запустіть бекенд (локально або через Docker Compose) і виконайте:

```powershell
cd frontend
npm run generate:api
```

Скрипт читає схему з <http://127.0.0.1:8000/openapi.json> і перезаписує `schema.d.ts`.
Закомітьте оновлений файл разом зі змінами бекенду. Короткі назви типів, якими
користується решта коду, оголошено у `frontend/src/api/types.ts`.

## Тести та перевірки

**Бекенд** (з активованим середовищем):

```powershell
cd backend
pytest
```

Тести не потребують ні справжніх ваг, ні Postgres. Модель у них — ResNet18 із випадковими
вагами, а історія зберігається в SQLite у пам'яті. Тести покривають збереження прогнозів,
пагінацію, фільтр, видалення, `/stats`, роботу без `DATABASE_URL` і з недоступною базою, а
також відповідність міграцій моделям. Один тест додатково перевіряє справжні ваги, якщо
файл `backend/models/resnet18_v2_best.pt` є на місці, а інакше пропускається.

**Вебінтерфейс:**

```powershell
cd frontend
npm test              # Vitest + React Testing Library, один прогін
npm run test:watch    # перезапуск тестів після змін
npm run typecheck     # перевірка типів TypeScript
npm run lint          # ESLint
npm run format:check  # Prettier; npm run format виправляє форматування
```

Тести вебінтерфейсу не звертаються до бекенду: `fetch` у них замокано. Вони перевіряють
сторінку аналізу (перевірку файлу, успішну відповідь, попередження, помилки), сторінку
історії (статистику, таблицю, пагінацію, фільтр, видалення, помилки 404 і 503),
перемикання сторінок і теми.

Якщо на комп'ютері мало вільної пам'яті (наприклад, поруч працює Docker), Vitest може
впасти з `JavaScript heap out of memory`. Тоді запустіть тести в одному процесі:
`npx vitest run --maxWorkers=1`.

## API

### `GET /health`

Повертає стан сервісу, пристрій і класи в порядку виходів моделі. Від бази не залежить.

```json
{"status": "ok", "device": "cpu", "classes": ["glioma", "meningioma", "notumor", "pituitary"]}
```

### `POST /predict`

Знімок передається у полі `file` запиту `multipart/form-data`. Параметр `gradcam=true`
додає до відповіді теплову карту.

```powershell
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict"
curl.exe -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true"
```

Приклад відповіді для знімка 640 × 480 без теплової карти:

```json
{
  "id": "43eb20d2-5203-42e7-8903-a86a82a76fbf",
  "predicted_class": "meningioma",
  "probabilities": {
    "glioma": 0.0012,
    "meningioma": 0.9988,
    "notumor": 0.00004,
    "pituitary": 0.0000001
  },
  "image_size": {"width": 640, "height": 480},
  "warnings": [
    {
      "code": "unexpected_image_size",
      "message": "Розмір знімка 640x480, а не 512x512. На знімках іншого розміру модель працює гірше і може пропустити гліому, бо в навчальних даних усі гліоми були 512x512."
    }
  ],
  "gradcam_png_base64": null
}
```

| Поле | Зміст |
|---|---|
| `id` | Ідентифікатор запису в історії; `null`, якщо історію вимкнено або запис не вдалося зберегти |
| `predicted_class` | Клас із найбільшою ймовірністю |
| `probabilities` | Ймовірності чотирьох класів; у сумі дають 1 |
| `image_size` | Розмір завантаженого знімка в пікселях |
| `warnings` | Список попереджень; порожній, якщо знімок має розмір 512 × 512 |
| `gradcam_png_base64` | Теплова карта у форматі PNG, закодована в base64; `null`, якщо її не просили |

Зберегти теплову карту у файл можна так:

```powershell
$r = curl.exe -s -F "file=@scan.jpg" "http://127.0.0.1:8000/predict?gradcam=true" | ConvertFrom-Json
[IO.File]::WriteAllBytes("$PWD\gradcam.png", [Convert]::FromBase64String($r.gradcam_png_base64))
```

### Помилки

| Код | Коли виникає |
|---|---|
| 400 | Файл порожній, не є зображенням або пошкоджений |
| 404 | Запису з таким `id` в історії немає |
| 413 | Файл більший за `MAX_UPLOAD_MB` або знімок має більше пікселів, ніж `MAX_PIXELS` |
| 415 | Зображення не у форматі JPEG чи PNG (наприклад, GIF, BMP, TIFF, WEBP) |
| 422 | Некоректний запит: немає поля `file`, неправильний `gradcam`, `limit`, `offset`, клас або `id` |
| 503 | Історію вимкнено (не задано `DATABASE_URL`) або база даних недоступна; лише для `/predictions` і `/stats` |

Тіло помилки має вигляд `{"detail": "..."}`. Для коду 422 у `detail` лежить стандартний
для FastAPI список помилок валідації.

Формат файлу визначається за його вмістом, а не за розширенням чи заголовком
`Content-Type`.

## Передобробка

Знімок проходить ті самі кроки, що й під час навчання та перевірки моделі
(`eval_tf2` у навчальному ноутбуці):

1. Перетворення в RGB.
2. `PadToSquare`: знімок розміщується по центру чорного квадрата.
3. `RandomAutocontrast(p=1.0)`.
4. `Resize((224, 224))`.
5. `ToTensor`.
6. `Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])`.

Порядок кроків міняти не можна: автоконтраст працює вже після додавання чорних полів.
Тест `test_transform_is_identical_to_training_notebook` перевіряє, що результат збігається
з кодом із ноутбука точно, до останнього значення.

## Grad-CAM

Теплова карта будується для передбаченого класу за виходом `layer4`, останнього
згорткового блоку ResNet18. Карта накладається на знімок у палітрі `jet`: червоні ділянки
вплинули на рішення моделі найбільше, сині — найменше. Картинка має розмір завантаженого
знімка; якщо його довша сторона перевищує 1024 пікселі, картинка зменшується до 1024.

Grad-CAM показує, на що зважала модель, а не межі пухлини. Карта має роздільність лише
7 × 7 клітинок і розтягується на весь знімок, тому вона груба.

## Примітки щодо залежностей

- **SQLAlchemy 2.0.** Використовується синхронний API SQLAlchemy 2.0 із драйвером psycopg 3.
  Код написано в стилі 2.0, тож перехід на 2.1 не потребуватиме змін.
- **TypeScript 6.0, а не 7.** Шаблон Vite ставить TypeScript 7, але `typescript-eslint`
  поки підтримує версії лише до 6.0. Коли з'явиться підтримка 7, версію можна підняти.
- **`overrides` для `openapi-typescript`.** Пакет оголошує сумісність лише з TypeScript 5.
  Його API для генерації типів у TypeScript 6 не змінилося, тому в `package.json` через
  `overrides` йому дозволено використовувати TypeScript проєкту, і `npm ci` працює без
  `--legacy-peer-deps`.
- **Кінці рядків.** `.gitattributes` вимагає LF у робочій копії на всіх системах, бо
  Prettier перевіряє саме LF.

## Обмеження

- **Розмір знімка.** У навчальних даних усі гліоми мали розмір 512 × 512, тому на знімках
  іншого розміру модель працює гірше. На тестовій вибірці з 1600 знімків вона розпізнала
  321 із 324 гліом розміру 512 × 512 (99,1 %) і лише 23 із 76 гліом інших розмірів (30,3 %).
  Для таких знімків сервіс додає попередження `unexpected_image_size`. Розмір тут є лише
  ознакою джерела знімка: якщо просто змінити розмір файлу до 512 × 512, попередження
  зникне, але надійність не зросте.
- **Дані.** Сервіс приймає окремі двовимірні зрізи у форматі JPEG або PNG. DICOM і
  тривимірні дослідження не підтримуються.
- **Чотири класи.** Модель завжди обирає один із чотирьох класів, навіть якщо на
  зображенні не МРТ мозку або є патологія іншого типу.
- **Безпека.** Автентифікації й обмеження частоти запитів немає: будь-хто з доступом до
  API бачить і може видаляти історію. Тому порти в Docker Compose відкрито лише на
  `127.0.0.1`, і сервіс не варто відкривати в публічну мережу.
- **Продакшн-збірка вебінтерфейсу** (nginx або віддача `dist` з FastAPI) ще не зроблена.
